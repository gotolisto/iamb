Written on 2026-11-22 by the reviewer of [`4.3-security-review.md`](4.3-security-review.md), who
took no part in the fixes. It checks commit `4615ae0` (migrations 11 to 18,
`server/restore/restore.py`, the new tests, ADR-0031, scenarios S85 to S87) and the section

## 4. New findings

The scripts run in a test database built as `server/tests/run.sh` builds its template, as the
tables' owner, with `set client_min_messages = notice`. `iamb_test.family('edit')` makes Ines (the
owner of a family), Tom (a member) and a stranger; `f1` is Ines's folder shared with the family to
change, `f2` her private folder, `s2` a snippet in `f2`.

### N1. An access entry begins in the middle of a request — high

- Where: `refresh_access` stamps a new access entry with the revision counter as it stands when the
  op that made the entry is applied (`…110700_steady_plans.sql:211`, `:235`); `version_readable`
  offers a version when the entry's `since_rev` is below the revision that replaced the version
  (`…110100_push.sql:54-80`); a push applies its ops in dependency order, folders before snippets,
  whatever order the device made them in (`…110100_push.sql:1083-1108`). Design: §5.4 ("the number
  says exactly which versions of a row the user could read through the entry"), ADR-0031 point 2,
  §6.3.
- What: the owner replaces private content in a snippet and then moves its folder into the shared
  tree (or renames a sub-folder and then moves the folder above it). When both changes travel in
  one push, the server moves the folder first and replaces the content second. The member's entry
  for the folder then "began before the version was replaced", and the version counts as one he
  could read, although no committed state of the database ever showed it to him and the owner
  replaced it before she shared. One push with both ops is what a device sends after any time
  offline, and whenever it sends its pending changes together (up to 200 ops).
- Direct read: needs the replaced version to be on offer in a conflict, which happens when the
  owner's edit was itself a stale write (her second computer). The member's own stale write then
  takes that conflict over, and `get_conflict` gives him the version; `resolve_conflict` lets him
  put it back as the row.

  ```sql
  do $$
  declare
      ids jsonb := iamb_test.family('edit');
      f1 uuid := (ids ->> 'f1')::uuid; f2 uuid := (ids ->> 'f2')::uuid; s2 uuid := (ids ->> 's2')::uuid;
      r0 bigint; rv bigint; r jsonb; c uuid;
  begin
      perform iamb_test.new_device('ines2', 'ines'); perform iamb_test.hello('ines2');   -- her second computer
      r0 := iamb_test.rev('snippet', s2);
      -- Her first computer writes something private into s2, in the private folder f2.
      perform iamb_test.push('ines', jsonb_build_array(iamb_test.op_snippet(s2, f2, ';priv', 'PIN of the safe: 4711', r0)));
      rv := iamb_test.rev('snippet', s2);
      -- Her second computer was offline and holds s2 at r0. There she empties the snippet and THEN moves
      -- the folder under the shared folder f1. The device sends both ops in one push, in that order.
      r := iamb_test.push('ines2', jsonb_build_array(
          iamb_test.op_snippet(s2, f2, ';priv', 'Nothing to see', r0),
          iamb_test.op_folder(f2, iamb_test.personal('ines'), f1, 'Private', iamb_test.rev('folder', f2))));
      raise notice 'owner push (edit, then move the folder under f1): % / %; conflict of her own: %',
          iamb_test.st(r, 1), iamb_test.st(r, 2), (r -> 'results' -> 0 ->> 'conflict') is not null;
      raise notice 'Tom''s access entry for f2 began at since_rev %; the private version (rev %) was replaced by rev %',
          (select since_rev from iamb.folder_access where user_id = iamb_test.uid('tom') and folder_id = f2), rv,
          (select replaced_by_rev from iamb.history where entity = 'snippet' and row_id = s2 and rev = rv);
      -- Tom (edit on f1, and now on f2 below it) sends a stale edit of s2 and reads the conflict it records.
      perform iamb_test.pull('tom');
      r := iamb_test.push('tom', jsonb_build_array(iamb_test.op_snippet(s2, f2, ';priv', 'Tom was here', 0)));
      c := (r -> 'results' -> 0 ->> 'conflict')::uuid;
      r := iamb_test.call('tom', format('api.get_conflict(iamb_test.dev(''tom''), 1, %L)', c));
      raise notice 'get_conflict offers Tom: %',
          (select string_agg(format('rev %s %L%s', v ->> 'rev', v -> 'row' ->> 'body',
                                    case when (v ->> 'taken_over')::boolean then ' (taken over)' else '' end), '; ' order by (v ->> 'rev')::bigint)
           from jsonb_array_elements(r -> 'versions') v);
      r := iamb_test.call('tom', format('api.resolve_conflict(iamb_test.dev(''tom''), 1, %L, ''restore'', %s)', c, rv));
      raise notice 'Tom restores the private version: %; the row now reads: %', r - 'epoch', (select body from iamb.snippet where id = s2);
  end $$;
  ```

  Result: `owner push (edit, then move the folder under f1): applied / applied; conflict of her
  own: t`; `Tom's access entry for f2 began at since_rev 14; the private version (rev 13) was
  replaced by rev 15`; `get_conflict offers Tom: rev 13 'PIN of the safe: 4711' (taken over); rev 15
  'Nothing to see'`; `Tom restores the private version: {"error": null, "state": "resolved"}; the
  row now reads: PIN of the safe: 4711`.

  On the hosted project, rolled back: the same (`n1_versions_tom_reads: [{"body": "PIN of the safe:
  4711", "taken_over": true}, {"body": "Nothing to see", "taken_over": false}]`). On the hosted
  project through the REST interface, with three real sessions of two throwaway accounts:
  `n1_get_conflict_as_member: {"http": 200, "error": null, "private_version_in_the_answer": true}`,
  `n1_member_restores_the_private_version: {"http": 200, "state": "resolved"}`. For a folder's name
  (h07): the member is offered `"PRIVATE-FOLDER-NAME divorce"`, the name a sub-folder had before the
  folder above it was moved into the shared tree in the same push.
- Without a conflict, one computer of the owner is enough for the oracle of finding 11:

  ```sql
  do $$
  declare
      ids jsonb := iamb_test.family('edit');
      f1 uuid := (ids ->> 'f1')::uuid; f2 uuid := (ids ->> 'f2')::uuid; s2 uuid := (ids ->> 's2')::uuid;
      rv bigint; r jsonb; guess text;
  begin
      -- Ines keeps a PIN in a snippet of her private folder f2.
      perform iamb_test.push('ines', jsonb_build_array(iamb_test.op_snippet(s2, f2, ';pin', 'PIN 4711', iamb_test.rev('snippet', s2))));
      rv := iamb_test.rev('snippet', s2);
      -- Later, on the same computer: she replaces the PIN, then moves the folder under the shared folder. One push.
      r := iamb_test.push('ines', jsonb_build_array(
          iamb_test.op_snippet(s2, f2, ';pin', 'ask me', rv),
          iamb_test.op_folder(f2, iamb_test.personal('ines'), f1, 'Private', iamb_test.rev('folder', f2))));
      perform iamb_test.pull('tom');
      foreach guess in array array['PIN 4710', 'PIN 4711', 'PIN 4712'] loop
          r := iamb_test.push('tom', jsonb_build_array(iamb_test.op_snippet(s2, f2, ';pin', guess, rv)));   -- base_rev: the revision of the old version
          raise notice 'guess %: the server names as author of the content: %', guess,
              coalesce((select a.name from iamb_test.actor a where a.user_id = (r -> 'results' -> 0 -> 'origin' ->> 'content_by')::uuid), 'nobody');
      end loop;
  end $$;
  ```

  Result: `guess PIN 4710: … tom`, `guess PIN 4711: … ines`, `guess PIN 4712: … tom`. The same on
  the hosted project, rolled back.
- Why the tests did not see it: `22_review_conflicts` and S85 move the snippet itself into the
  shared folder, or share the folder in a request of its own. No test has the change of access and
  the edit in one request. With two requests the rule is exact.
- Fix: a new entry must begin at or above every revision its request draws. Stamp `since_rev` when
  the request ends (the last step already writes the feed: set the entries made in this transaction
  to the counter's value then), or keep the transaction with the entry and let `version_readable`
  refuse a version that was replaced in the transaction that made the entry. Say in §5.4 and
  ADR-0031 that "while the entry existed" means "in a state the reader could have seen", and add a
  scenario with both ops in one push.

### N2. A cascade list costs temporary files without bound, and the request is not counted — medium

- Where: before the fixes the answer to a cascade list had no bound and was built entry by entry
  (findings 7 and 18). Now it is one statement and stays within 4 MiB, but the statement
  `cascade_answer` runs joins every listed row the caller can read with its whole wire form and
  sums the sizes in a window over the list (`…110100_push.sql:304-312`); only afterwards does it
  decide which rows go into the answer whole. The window sorts and keeps every row it was given.
  The function is reached without any folder: a delete of a folder the server does not know is
  answered `unchanged` with the cascade answer (`:538-545`), and a replayed op computes it again
  (`:1151`). `api.push` catches two classes of error and no other (`:1206`).
- What: the caller stores a few large rows of his own (one snippet of 400 kB is enough) and names
  them many times in the cascade list of one op. A list may have 20,000 entries; two such ops fit
  into one request of 4 MiB. Locally (ten snippets of 400 kB, work_mem 4 MB):

  | Entries in the list | Request | Time | Answer | Temporary files written |
  | --- | --- | --- | --- | --- |
  | 100 | 8 kB | 0.2 s | 3.6 MB | 38 MB |
  | 1,000 | 84 kB | 1.5 s | 3.7 MB | 383 MB |
  | 4,000 | 336 kB | 7.3 s | 3.7 MB | 1,531 MB |
  | 20,000 | 1.7 MB | stopped after 18 s: `could not write to file … No space left on device` (5.8 GB were free) | — | all of the disk |

  On the hosted project, rolled back and small on purpose (one snippet of 400 kB): 50 entries
  31 MB and 0.24 s, 100 entries 53 MB and 0.36 s, 250 entries 111 MB and 2.3 s. The hosted
  database has `temp_file_limit = -1` (no limit) and `work_mem` 2 MB; `push` is declared with a
  time-out of 20 s, the REST role's own is 8 s. Larger lists were not run there: the point of the
  finding is that they would fill its disk. The space is given back when the statement ends, so
  what one account can hold at a time is one request's worth per session; a device runs one push
  at a time, an account can have several devices, and one person several accounts.
- Not counted: a request that ends in an error outside the two caught classes undoes its own
  count. Run locally with small sizes: a request stopped for temporary file space
  (`temporary file size exceeds temp_file_limit`): `push_calls` 1 before, 1 after; a request cut
  off by the time-out (`canceling statement due to statement timeout`): 1 after; a request that
  ends normally: 2. So the rate limit of 60 pushes a minute does not apply to exactly the
  requests that cost most.
- Reproduction (psql; set `temp_file_limit` on the test cluster first):

  ```sql
  -- once: an account with no group and no share, and ten snippets of 400 kB of her own (4 MB, inside every limit)
  create table iamb_test.big (id uuid);
  insert into iamb_test.big select gen_random_uuid() from generate_series(1, 10);
  do $$
  declare sf uuid := gen_random_uuid();
  begin
      delete from iamb_test.actor where true;
      perform iamb_test.new_user('mallory'); perform iamb_test.hello('mallory', 'Mallory');
      perform iamb_test.push('mallory', jsonb_build_array(iamb_test.op_folder(sf, iamb_test.personal('mallory'), null, 'own')));
      perform iamb_test.push('mallory', (select jsonb_agg(iamb_test.op_snippet(id, sf, ';b', repeat('x', 400000))) from iamb_test.big));
  end $$;
  -- per size (psql -v n=1000): one push with one op, the delete of a folder that does not exist,
  -- whose cascade list names her ten snippets n/10 times each
  select temp_bytes as b0 from pg_stat_database where datname = current_database() \gset
  \timing on
  select iamb_test.st(r) as status, jsonb_array_length(r -> 'results' -> 0 -> 'cascade') as entries, octet_length(r::text) / 1000 as answer_kb
  from (select iamb_test.push('mallory', jsonb_build_array(iamb_test.op_delete('folder', gen_random_uuid(), 0, jsonb_build_object('cascade',
          (select jsonb_agg(jsonb_build_object('entity', 'snippet', 'id', b.id, 'base_rev', 0)) from iamb_test.big b, generate_series(1, :n / 10)))))) as r) x;
  \timing off
  select pg_sleep(1.5), pg_stat_clear_snapshot();
  select pg_size_pretty(temp_bytes - :b0) as temporary_files_written from pg_stat_database where datname = current_database();
  ```

  Result for `n=100`: `unchanged|100|3616`, 0.2 s, `38 MB`; for `n=1000`: `unchanged|1000|3717`,
  1.3 to 1.5 s, `383 MB`.
- Fix: decide which entries get a whole row from sizes alone (the stored row's size, one entry
  per distinct row), and read the wire form only of those; refuse or fold a list that names a row
  twice. For the owner: `temp_file_limit` on the hosted database, so that one statement cannot take
  the disk whatever a function does. The count of a request that is cut off cannot be kept by the
  request itself; that stays with a limit in front of the database, as §11 says.

### N3. Two ways left to stall somebody else's writes — medium

- (a) A reader holds the profile's lock. `push_core` locks every profile the caller "has a grant
  in", and any access entry is a grant, `view` included (`…110100_push.sql:39-46`, `:1115`,
  `:1126`). The lock is taken before the op is judged, so an op that is then refused holds it for
  the whole request. The review's finding 6 was about a stranger; a person the owner shared one
  folder with, to read, can do the same to her whole personal profile. With N2 he has requests that
  run to the time-out and are not counted. The hosted REST role has `lock_timeout = 8s`: the
  owner's request does not only wait, it fails.

  Set-up: `select iamb_test.put('ids', iamb_test.family('view')); select iamb_test.pull('tom'), iamb_test.pull('ines');`

  ```sql
  -- session 1: Tom, who may only read f1
  begin;
  select 'session 1 (Tom, view only): ' || iamb_test.st(iamb_test.push('tom', jsonb_build_array(
      iamb_test.op_snippet(gen_random_uuid(), (iamb_test.get('ids') ->> 'f1')::uuid, ';x', 'x'))));
  select pg_sleep(5);    -- stands for the time the request works
  commit;
  ```

  ```sql
  -- session 2, started a second later: Ines saves a snippet in her PRIVATE folder f2
  \timing on
  select 'session 2 (Ines, her private folder): ' || iamb_test.st(iamb_test.push('ines', jsonb_build_array(iamb_test.op_snippet((iamb_test.get('ids') ->> 's2')::uuid,
      (iamb_test.get('ids') ->> 'f2')::uuid, ';priv', 'edited', iamb_test.rev('snippet', (iamb_test.get('ids') ->> 's2')::uuid)))));
  ```

  Result: `session 1 (Tom, view only): rejected:forbidden`; `session 2 (Ines, her private folder):
  applied` after 4.1 s. With `set lock_timeout = '2s'` in session 2: `ERROR: canceling statement
  due to lock timeout … while locking tuple … in relation "profile"`.
- (b) The lock on a row's id has a 32-bit key: `hashtext(entity || ':' || id)`
  (`…110100_push.sql:1132-1138`). Two ids with one key share a lock. For a given id of a victim's
  row an attacker finds an id of his own with the same key by trying about 2^32 ids on his own
  machine; then a create of his own row in his own profile holds the victim's row lock while his
  request runs. (Naming the victim's id itself takes no lock; the colliding id does.)

  ```sql
  -- set-up: two ids with one key (here found among 400,000 random ids), Ines's private snippet with the first
  select iamb_test.put('ids', iamb_test.family('edit')) is not null;
  select iamb_test.pull('stranger') ->> 'error', iamb_test.pull('ines') ->> 'error';
  create table iamb_test.pair as
  with c as (select gen_random_uuid() as id from generate_series(1, 400000)),
       h as (select id, hashtext('snippet:' || id::text) as k from c),
       d as (select k from h group by k having count(*) > 1 limit 1)
  select (array_agg(h.id order by h.id))[1] as a, (array_agg(h.id order by h.id))[2] as b from h join d using (k);
  select iamb_test.st(iamb_test.push('ines', jsonb_build_array(iamb_test.op_snippet((select a from iamb_test.pair), (iamb_test.get('ids') ->> 'f2')::uuid, ';a', 'private row A'))));
  select iamb_test.put('sf', to_jsonb(gen_random_uuid())) is not null;
  select iamb_test.st(iamb_test.push('stranger', jsonb_build_array(iamb_test.op_folder((iamb_test.get('sf') #>> '{}')::uuid, iamb_test.personal('stranger'), null, 'own'))));
  ```

  ```sql
  -- session 1: the stranger (no group, no share) creates a snippet with the second id in his OWN folder; his request stays open
  begin;
  select 'session 1 (stranger, his own folder, id B): ' || iamb_test.st(iamb_test.push('stranger', jsonb_build_array(
      iamb_test.op_snippet((select b from iamb_test.pair), (iamb_test.get('sf') #>> '{}')::uuid, ';b', 'b'))));
  select pg_sleep(5);
  commit;
  ```

  ```sql
  -- session 2, started a second later: Ines edits her private snippet A
  \timing on
  select 'session 2 (Ines edits her private row A): ' || iamb_test.st(iamb_test.push('ines', jsonb_build_array(iamb_test.op_snippet((select a from iamb_test.pair),
      (iamb_test.get('ids') ->> 'f2')::uuid, ';a', 'edited', iamb_test.rev('snippet', (select a from iamb_test.pair))))));
  ```

  Result: `session 1 (stranger, his own folder, id B): applied`; `session 2 (Ines edits her private
  row A): applied` after 4.2 s.
- Fix: (a) take a profile's lock only for a caller who can write something in it (the op's own
  permission, or `edit` on some folder of the profile), and answer the rest without it; (b) a key
  that cannot be made to collide: all 128 bits of the id (the two-key form of the advisory lock
  takes two 32-bit numbers; the one-key form takes 64; neither holds an id, so a row in a small
  table keyed by entity and id is the exact form).

### N4. A live folder on a fifth level — low, present before the fixes

- Where: a move counts only the live folders below the folder it moves
  (`subtree_height`, `…100200_private_helpers.sql:972-982`, used at `…110100_push.sql:697`), and a
  put that restores a deleted folder under the parent it had is not checked for depth (`:704`).
- What: delete a sub-folder, move its parent to the fourth level, restore the sub-folder.

  ```sql
  do $$
  declare
      p uuid; a uuid := gen_random_uuid(); b uuid := gen_random_uuid(); c uuid := gen_random_uuid();
      x uuid := gen_random_uuid(); y uuid := gen_random_uuid(); r jsonb; depth integer;
  begin
      delete from iamb_test.actor where true;
      perform iamb_test.new_user('ines'); perform iamb_test.hello('ines', 'Ines');
      p := iamb_test.personal('ines');
      r := iamb_test.push('ines', jsonb_build_array(
          iamb_test.op_folder(a, p, null, 'A'), iamb_test.op_folder(b, p, a, 'B'), iamb_test.op_folder(c, p, b, 'C'),   -- three levels
          iamb_test.op_folder(x, p, null, 'X'), iamb_test.op_folder(y, p, x, 'Y')));                                       -- X with a child Y
      r := iamb_test.push('ines', jsonb_build_array(iamb_test.op_delete('folder', y, iamb_test.rev('folder', y))));        -- Y is deleted
      r := iamb_test.push('ines', jsonb_build_array(iamb_test.op_folder(x, p, c, 'X', iamb_test.rev('folder', x))));       -- X moves under C: level 4
      raise notice 'move of X under C (level 3): % adjusted %', iamb_test.st(r), r -> 'results' -> 0 -> 'adjusted';
      r := iamb_test.push('ines', jsonb_build_array(iamb_test.op_folder(y, p, x, 'Y', iamb_test.rev('folder', y))));       -- Y is restored where it was
      raise notice 'restore of Y under X: % adjusted %', iamb_test.st(r), r -> 'results' -> 0 -> 'adjusted';
      with recursive up as (select f.id, f.parent_id, 1 as d from iamb.folder f where f.id = y
                            union all select g.id, g.parent_id, up.d + 1 from iamb.folder g join up on g.id = up.parent_id where up.d < 10)
      select max(d) into depth from up;
      raise notice 'Y is live: %, on level %', (select deleted_at is null from iamb.folder where id = y), depth;
      begin perform iamb_test.check_tree(); raise notice 'check_tree: holds';
      exception when others then raise notice 'check_tree: %', sqlerrm; end;
  end $$;
  ```

  Result: `move of X under C (level 3): applied adjusted []`; `restore of Y under X: applied
  adjusted []`; `Y is live: t, on level 5`; `check_tree: check failed: no cycle and at most four
  levels`. The same against the ten original migrations, and on the hosted project, rolled back.
- How it was found, and a correction to the review: the fuzz, run with handovers of ownership for
  the first time, stopped at the tree check in 3 of 14 runs (a tombstone on a fifth level after a
  move). Against the ten original migrations it stops there too (2 of 6 runs). The review's line
  "I7 … held" over 7,800 steps was luck: a seed does not fix a run, because the ids are random.
- Fix: count deleted folders in `subtree_height`, or check the depth when a folder is restored and
  put it under the nearest folder above, as a create does.

### N5. A deleted row keeps its content for whoever can read its folder now — medium, for the owner to decide

- Where: a tombstone is the row with `deleted_at` set, content and all (it must be, so that
  "bring it back" works). The snippet policy asks only whether the reader has an access entry for
  the folder; `snapshot` returns tombstones (`…110600_reads_and_grants.sql:134`) and `rows` returns
  any row "as the caller may read it now". The design says both: §4.4 "every snippet in those
  folders", §6.5 "tombstones the server still holds".
- What: the owner deletes a snippet and shares its folder afterwards; or a member joins after a
  snippet of the shared folder was deleted. For 30 days after the delete the newcomer's `snapshot`
  and `rows` carry the deleted text. (`fetch_folder`, which a device calls for a folder that became
  visible, returns live rows only; a `snapshot` is what a device calls when it registers.)

  ```sql
  do $$
  declare
      ids jsonb := iamb_test.family('edit');
      f1 uuid := (ids ->> 'f1')::uuid; f2 uuid := (ids ->> 'f2')::uuid; s2 uuid := (ids ->> 's2')::uuid;
      r jsonb; snap jsonb;
  begin
      perform iamb_test.push('ines', jsonb_build_array(iamb_test.op_snippet(s2, f2, ';priv', 'DELETED-SECRET 4711', iamb_test.rev('snippet', s2))));
      perform iamb_test.push('ines', jsonb_build_array(iamb_test.op_delete('snippet', s2, iamb_test.rev('snippet', s2))));
      -- only now is the private folder shared (moved under the shared folder)
      perform iamb_test.push('ines', jsonb_build_array(iamb_test.op_folder(f2, iamb_test.personal('ines'), f1, 'Private', iamb_test.rev('folder', f2))));
      r := iamb_test.pull('tom');
      snap := iamb_test.call('tom', 'api.snapshot(iamb_test.dev(''tom''), 1, null, null)');
      raise notice 'pull carries the deleted body: %; snapshot carries it: %; rows() carries it: %; fetch_folder carries it: %',
          r::text like '%DELETED-SECRET%', snap::text like '%DELETED-SECRET%',
          iamb_test.call('tom', format('api.rows(iamb_test.dev(''tom''), 1, %L::jsonb)', jsonb_build_array(jsonb_build_object('entity', 'snippet', 'id', s2))))::text like '%DELETED-SECRET%',
          iamb_test.call('tom', format('api.fetch_folder(iamb_test.dev(''tom''), 1, %L)', f2))::text like '%DELETED-SECRET%';
  end $$;
  ```

  Result: `pull carries the deleted body: f; snapshot carries it: t; rows() carries it: t;
  fetch_folder carries it: f`. For a member who joins later: her snapshot carries the body of the
  snippet deleted before she joined (locally her access entry began at revision 17; the delete was
  revision 14). Both forms the same on the hosted project, rolled back (h07); the first also
  against the ten original migrations.
- Why it is here although the design allows it: ADR-0031 now withholds a version that was replaced
  before the reader's access began. A row that was deleted before the reader's access began is the
  same case to the person who deleted it, and it is handed over whole. It is not counted against
  the KPI, because no rule of the design is broken; if the owner reads the KPI as "nothing she
  removed before sharing reaches a member", this is a second miss.
- Options: do not deliver a tombstone (or deliver it without content) to a reader whose access
  entry began at or after the revision of the delete, which `since_rev` now makes cheap; or keep
  the behaviour and say it in §4.4 and in the share dialog ("snippets deleted from this folder in
  the last 30 days are shared too").

### N6. A party closes a conflict whose versions he is not offered — low

- Where: `resolve_conflict … keep` needs a party who can read the row and closes the conflict for
  everybody (`…110200_conflicts.sql:136-140`). Since ADR-0031 a party may be offered fewer versions
  than the conflict holds.
- What: the owner has an open conflict of her own about a private version. The snippet comes into
  the shared folder; the member's stale write takes the conflict over (he is offered only the
  version his write replaced) and he closes it. The owner's conflict is gone from her list and
  the version cannot be restored through any call; the history row stays until the purge.

  ```sql
  do $$
  declare
      ids jsonb := iamb_test.family('edit');
      f1 uuid := (ids ->> 'f1')::uuid; f2 uuid := (ids ->> 'f2')::uuid; s2 uuid := (ids ->> 's2')::uuid;
      r1 bigint; priv bigint; r jsonb; c uuid;
  begin
      perform iamb_test.new_device('ines2', 'ines'); perform iamb_test.hello('ines2');
      r1 := iamb_test.rev('snippet', s2);
      -- Her two computers disagree about a snippet in her private folder; the conflict stays open (she has not decided).
      perform iamb_test.push('ines',  jsonb_build_array(iamb_test.op_snippet(s2, f2, ';priv', 'her lost private version', r1)));
      priv := iamb_test.rev('snippet', s2);
      perform iamb_test.push('ines2', jsonb_build_array(iamb_test.op_snippet(s2, f2, ';priv', 'Nothing to see', r1)));
      -- She moves the snippet into the shared folder. Tom's stale edit takes her conflict over.
      perform iamb_test.push('ines2', jsonb_build_array(iamb_test.op_snippet(s2, f1, ';priv', 'Nothing to see', iamb_test.rev('snippet', s2))));
      perform iamb_test.pull('tom');
      r := iamb_test.push('tom', jsonb_build_array(iamb_test.op_snippet(s2, f1, ';priv', 'Tom was here', 0)));
      c := (r -> 'results' -> 0 ->> 'conflict')::uuid;
      raise notice 'offered to Tom: %', (select jsonb_agg(v -> 'row' -> 'body') from jsonb_array_elements(
          iamb_test.call('tom', format('api.get_conflict(iamb_test.dev(''tom''), 1, %L)', c)) -> 'versions') v);
      raise notice 'Tom closes it: %', iamb_test.call('tom', format('api.resolve_conflict(iamb_test.dev(''tom''), 1, %L, ''keep'')', c)) - 'epoch';
      raise notice 'Ines restores her private version afterwards: %; the row reads: %; her open conflicts: %',
          iamb_test.call('ines', format('api.resolve_conflict(iamb_test.dev(''ines''), 1, %L, ''restore'', %s)', c, priv)) - 'epoch',
          (select body from iamb.snippet where id = s2),
          jsonb_array_length(iamb_test.call('ines', 'api.conflicts(iamb_test.dev(''ines''), 1)') -> 'conflicts');
  end $$;
  ```

  Result: `offered to Tom: ["Nothing to see"]`; `Tom closes it: {"error": null, "state":
  "resolved"}`; `Ines restores her private version afterwards: {"error": null, "state":
  "resolved"}; the row reads: Tom was here; her open conflicts: 0`. The same on the hosted project,
  rolled back.
- Fix: "keep" by a party who is not offered every version closes the conflict for that party only
  (or for the parties who are offered no more than he is); it stays open for the others.

### N7. An upload outlives the uploader's right — low today, to settle before task 4.6

- Where: nothing ends a person's open uploads when their membership or the share ends
  (`end_membership`, `…110300_account.sql:164-199`); `api_service.attachment_verified` records the
  file and marks the uploader's attachment rows as backed without asking whether the uploader may
  still write in the profile (`…110400_uploads.sql:160-215`); the storage policy lets the uploader
  send the object for as long as the upload row exists.
- What: a member opens an upload in the owner's profile and links an attachment row with that
  hash to a shared snippet; he is removed; the upload is committed. A file is recorded in the
  profile he left (it counts against the owner's allowance), and the row he left behind becomes
  backed, so the bytes he sends after his removal are served to the folder's readers.

  ```sql
  do $$
  declare
      ids jsonb := iamb_test.family('edit'); g uuid := (ids ->> 'g')::uuid; p uuid := (ids ->> 'p_ines')::uuid; s1 uuid := (ids ->> 's1')::uuid;
      r jsonb; up uuid; sha text := repeat('5a', 32); a uuid := gen_random_uuid();
  begin
      -- Tom (edit on the shared folder) opens an upload in Ines's profile and links an attachment row with that hash to the shared snippet.
      up := (iamb_test.call('tom', format('api.attachment_upload_begin(iamb_test.dev(''tom''), 1, %L, %L, 1000, ''image/png'')', p, sha)) ->> 'upload')::uuid;
      perform iamb_test.pull('tom');
      r := iamb_test.push('tom', jsonb_build_array(iamb_test.op_attachment(a, p, sha), iamb_test.op_snippet_attachment(gen_random_uuid(), s1, a)));
      raise notice 'row and link: % / %; backed: %', iamb_test.st(r, 1), iamb_test.st(r, 2), (select backed from iamb.attachment where id = a);
      -- Ines removes Tom.
      perform iamb_test.call('ines', format('api.remove_member(iamb_test.dev(''ines''), 1, %L, %L)', g, iamb_test.uid('tom')));
      raise notice 'after the removal: Tom may edit in her profile: %; his open uploads there: %',
          iamb_private.edits_in_profile(iamb_test.uid('tom'), p), (select count(*) from iamb.attachment_upload where uploaded_by = iamb_test.uid('tom') and profile_id = p);
      -- The commit, as the service would call it once the bytes are there.
      r := api_service.attachment_verified(up, sha, 1000);
      raise notice 'commit: %; file rows in her profile for that hash: %; his attachment row backed: %',
          r, (select count(*) from iamb.attachment_blob where profile_id = p and sha256 = sha), (select backed from iamb.attachment where id = a);
  end $$;
  ```

  Result: `row and link: applied / applied; backed: f`; `after the removal: Tom may edit in her
  profile: f; his open uploads there: 1`; `commit: {"done": true, "error": null}; file rows in her
  profile for that hash: 1; his attachment row backed: t`. The same on the hosted project, rolled
  back.
- Why low today: only the service role can call the function, and the edge function that will
  call it for a device does not exist yet. With it, this is a write after the removal (G13).
- Fix: end a person's open uploads in a profile when their right to write there ends, or let
  `attachment_verified` answer as for an upload that does not exist when
  `edits_in_profile(uploaded_by, profile_id)` is false.

## 6. What was tried against the new code and held

- **The party rule.** `conflict_history` and `member_addresses`, called directly as a stranger, as a
  removed member who is still in `parties`, and as a member who is no party: nothing. `get_conflict`,
  `conflicts`, `resolve_conflict`: `not_found` or empty. The tables `history`, `tx_feed`, `tx_rows`:
  `permission denied`. Through REST the schemas `iamb` and `iamb_private` are not reachable at all
  (`PGRST106`), `api_service` answers a user with 403, `api` answers the public key alone with 401.
- **The create path.** One request that names one new id in two profiles: the first op is applied,
  the second `blocked:invalid`, in both orders; two requests in parallel: the second waits and is
  `blocked:invalid`; an attachment row made that way in the owner's profile is not backed. The same
  id for a folder and a snippet is accepted (ids are unique per table) and breaks nothing.
- **Locking order.** No deadlock was found in the two-connection runs; the order is the device's
  row, the profiles (groups first), the ids, the feed heads, in every path read.
- **Uploads.** 20 open per account across profiles; a size of 0 refused; an ended upload's object
  refused; ending needs the uploader or whoever manages the profile.
- **The rate counters.** `revoke_device` and `sign_out_everywhere` are counted per calling device;
  a device cannot use up another's.
- **Retention.** One profile takes at most a quarter of a run; the run goes on where the last
  stopped.
- **Sessions.** The 28 claim shapes answer as before; a session past `not_after` is refused by
  `enter` and by every policy.
- **The fuzz.** 14 seeds of 560 steps with handovers of ownership (41 succeeded): after every step
  the access entries equal the slow reference, the tree has no cycle and nothing live under a
  deleted folder, no entry begins in the future; every tenth step the policies give each of the
  five accounts exactly the rows `readers()` names. With the count of levels in the check, 3 of 14
  runs stop at N4.
