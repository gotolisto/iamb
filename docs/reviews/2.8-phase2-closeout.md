## 1. Verdict

Phase 2's privacy gate can close: no high and no medium finding is open.

- **N1 is fixed.** Each request names the trigger's window, and every injector compares it with
  where keys go right before its start marker. In the follow-up review's probe the expansion
  reached the password field in 0 of 300 rounds in each of its six cases, three runs each
  (before the fix, same probe, same machine: up to 300). Demonstrated on the mock; by reading on
  Windows and macOS, whose injector protocols ran here on their recorded desks.
- **Finding 5 on macOS is fixed, by reading.** A key press now carries a process, and the engine
  thread drops a key whose process is not the one of the last focus report, as on Windows. What
  a Mac still has to show is which of the two sources stamps real keys (section 3); with the second
  one a short part of the original window stays (C1, low).

I found no new high or medium finding and five low ones (C1 to C5). Two are races in the new
code (C2, C3); the other three say where the fix ends: on macOS it is as late as the system's own
notification (C1), an injector's check and its send are two moments (C4), and the one check of
the macOS stamp can be skipped without a failure (C5). None is a reason to hold the gate. C1 and
C5 belong in the lab run of task 2.7.

**False positives of the start check.** I found none. The check adds no system call: it compares
a reading every injector already made. On Windows that is the foreground window and its process,
the two numbers of the watcher's token and of the key stamp, none of which waits for the window.
On macOS it is the workspace's frontmost application, where the token's process comes from too;
the token's window is not compared. Without a focus report and without a stamp the request has no
target and nothing is compared; with a report the target is the report's window, so a missing
stamp changes nothing. In the 2-minute soak 199 of 199 expansions were typed and the worker log
holds neither `injection_focus_moved` nor `keys_for_unreported_window`.

**Stale or wrong stamps on macOS, by reading.** With the event's field empty, a key is unstamped
only before a watcher's first look, after its thread ended (the service suspends the engine when
it sees that) or when no application is frontmost. A stamp that names another process than the
report makes keys dropped, never let through; the inspector's contradiction turns that off after
half a second, which is the behaviour before the fix, not worse. A password field with secure
keyboard entry on is not touched by any of this: its keys do not reach the tap.

## 3. What the macOS runner's check will and will not show

`keys_are_stamped_with_this_process` (`crates/iamb-platform-macos/tests/focus.rs:658`) posts a
Left key while the test's own window is in front and prints `note: key stamp source: …`.

- It shows: that a posted key reaches the sink stamped with the test's own process, and whether
  the event's own field was filled in for a session tap. A field that names something else fails
  the check; so does a key that arrives unstamped.
- It does not show: the same for a key from a real keyboard; anything about a key typed right
  after another application came to the front, which is what finding 5 is about (the check
  waits 300 ms first); a window of a helper process; that the stamp is right for another process
  than the one that posted the key (poster, frontmost application and expected stamp are the
  same process).
- It is skipped, not failed, when the watcher or the listener cannot start (no Accessibility or
  Input Monitoring grant), when the window is not in front, or when secure keyboard entry is on.
  A green macOS job therefore does not say the check ran (C5).

## 4. New findings

Severity as in the two reviews before. All five are low.

### C1. macOS: with the event's field empty, the stamp and the start check are as late as the activation notification — low, by reading

- Where: `crates/iamb-platform-macos/src/listener/target.rs:82`,
  `focus/watcher.rs:180-192` (the atomic is written when the notification reaches the main
  thread), `focus/system.rs:10` and `:62` (the workspace's frontmost application "is refreshed as
  the main run loop turns"; the injector's start check reads it).
- What: between the moment the system sends keys to another application and the turn of the
  worker's main run loop that hears of it, the atomic still names the previous application, and
  so does the workspace. A key typed then is stamped with the previous process and handled with
  its verdict, as before the fix; an injector that looks then starts. What the fix removes is
  the rest of the old window: the watcher's look and two thread hops. If the event's field is
  filled in, none of this applies.
- Failure scenario: a window of an excluded application takes the focus while the user types,
  and the next key lands before the notification. It is matched as text of the previous
  application; if it is a trigger, the expansion can start there. Password fields that switch
  secure keyboard entry on are not affected.
- Not known: how long that time is, and which source stamps real keys.
- Fix: read the runner's note. If it names the frontmost application, measure in the lab (switch
  application and type at once, M-cells of the matrix) and add the limit to architecture §8,
  "Detection limits", which has no row for it. For the start check it is worth trying on a Mac
  whether the window server's list (`front_window` reads it without asking an application) is
  ahead of the workspace.

### C2. macOS: a look under way can overwrite the newer note of the frontmost application — low, by reading

- Where: `crates/iamb-platform-macos/src/focus/watcher.rs:396-400` against `:191`.
- What: `look` reads the workspace, then the window list (a call to the window server), then
  stores the process it read. An activation notification that arrives in between stores the new
  process first, and the look overwrites it with the old one. It stays until the watcher's next
  look, at the latest after the upkeep of the current turn (Accessibility messages, up to
  100 ms each).
- Failure scenario: an application is activated while a look for a window or timer signal is
  under way. For the rest of that turn keys for the new application carry the old stamp, so the
  window C1 describes is one watcher turn longer.
- Fix: let the main thread count its notes and the look store only if the count did not move
  since it read the workspace.

### C3. The service's own focus read takes the application and the window in two calls — low, demonstrated on the mock

- Where: `crates/iamb-service/src/worker/engine.rs:487`.
- What: `resync` calls `focused_app()` and `focus_token()` one after the other and sends both to
  the focus thread as one change. If the focus moves between them, one application's name is
  paired with another's window; the exclusion is judged by the name, the keys by the window.
- Shown by: a probe on the fixed code. `org.example.chat` is excluded, focus reports are held, a
  third window takes the focus, three keys are typed there, and the chat window takes the focus
  between the two reads. `brb ` typed in the chat window then became `be right back `, and
  `suspended_excluded_app` was not recorded. A report of the watcher for that window corrects
  it.
- Why low: it takes a focus change inside two adjacent calls, during the lag N5 is about.
- Fix: one inspector call that returns both from one reading, as the watchers build theirs.

### C4. An injector's check and its send are two moments; ADR-0026 item 3 says more — low, demonstrated on the mock

- Where: `crates/iamb-platform/src/mock/mod.rs:1062-1075`,
  `crates/iamb-platform-windows/src/injector/run.rs:157`,
  `crates/iamb-platform-macos/src/injector/run.rs:365`;
  `docs/decisions/0026-enter-and-tab-not-default-delimiters.md:10`.
- What: the guard reads the focus and the step is sent after it. A window that takes the focus
  in between receives that step: the deletion, the text or the retyped trigger.
- Shown by: my sweep in section 5. With the focus change aimed at the injection (0.1 to 0.35 ms
  after the trigger key), a step reached the password field in 44 and 51 of 7,200 rounds in two
  runs, at most 10 of 300 in one case; before the fix 1,897 of 7,200. Each time the field lost four
  characters, or gained the text or the trigger. All of them are changes after the start
  check: the gap before it is closed, this is the one after each later check.
- Why low: the window is the time between two adjacent calls, about a thousand times shorter
  than N1's, and no system offers a check and a send in one step. The mock should not hide it by
  holding its lock over both.
- Fix: none in the code. ADR-0026 item 3 says such a trigger "sends nothing there, whether the
  move came before the start marker or after it"; say "at most the step being sent". The figures
  it gives as the follow-up review's (286 to 300, 4 to 5) are from another run of the probe; the
  review has 299 to 300, 2 and 4.

### C5. The check of the macOS stamp can be skipped unseen, and the watcher's writes have no other test — low

- Where: `crates/iamb-platform-macos/tests/focus.rs:665`, `:673`, `:883`;
  `focus/watcher.rs:191`, `:399`, `:513`.
- What: section 3. The three places that write the atomic exist only on macOS; removing them
  fails no test that runs here, and on a runner without the grants the one test that needs
  them is skipped. `.github/workflows/ci.yml` does not require it.
- Fix: run the check in the lab with the grants and keep its note with the 2.7 results, or let a
  variable turn its skip into a failure as `IAMB_REQUIRE_DESKTOP` does on Windows.

## 6. What else was read, without a finding

- **The request's target.** It is set where the batch is made, on the engine thread, so it is the
  focus the trigger was accepted under; a form's or the palette's request gets the window it was
  parked for. A request that waits behind another injection is checked when its turn comes.
- **N5's episode logic.** One diagnostic per run of such keys; the focus is read at most every
  half second; a focus change ends both the count and the distrust. The inspector's two reads
  (`NSWorkspace` and the window list on macOS, the foreground window and its process image on
  Windows) send no message to the application, so a hung one cannot hold the engine thread.
- **The watcher's note on macOS.** Cleared when the watcher thread ends, written only while a
  watcher lives, never from the tap. The activation observer still does nothing slow on the
  main thread: one dictionary read and one store.
- **Documents.** Architecture §3, §4.6 and §6.1 and ADR-0026 say what the code does, C1 and C4
  apart.
