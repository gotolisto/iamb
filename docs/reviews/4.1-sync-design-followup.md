## 1. Result

**Of the first review's 21 high and medium findings, 16 are resolved, 5 partly, none is
unresolved; all five high findings are resolved. New: 1 high, 6 medium, 8 low.** The design is
close to one the later tasks can build from, and not there yet.

The revision is thorough where the first review pointed. The handed-out mark, the answers for a
cascade and the note of skipped rows close the two sequences in which a device moved past a row
for good (findings 1 and 2); I found no other sequence of that kind without a restore. The lock
order of C24 holds for every pair of requests I tried, including the three interleavings of
finding 3. Authorship against the base version (C17) and the order by author and `created_rev`
(D13) close findings 4 and 5: I found no write, stale or not, and no copy or re-push by which a
member's content comes to count as the reader's, and no way for a member's snippet to take an
abbreviation from one whose content the reader wrote. D13 uses only what the server sends, so
every device of a user orders alike once it has synced.

What is open is mostly in the corners the revision added, and in three places where a fix stops
one step short:

- **After a restore an edit can be lost silently (N1, high).** A change the restore lost, and
  that another device overwrote in the new epoch before its holder returned, is replaced on the
  holder's device without a conflict and is then nowhere. §14 puts a restore inside the
  simulation that measures "0 lost edits", so this is a sequence that simulation will find.
- **Three fixes are partly effective.** A member who may change a shared folder can still read a
  file of the owner's private library whose hash they know, by linking a row of their own to it
  (N3, the rest of finding 9). A revoked device can register again once its revoked row is
  removed after 30 days, because nothing ends its session (N4, the rest of finding 10). When a
  sub-tree leaves a shared folder, the member's device is told to remove the folder row before
  it is told to purge the tree, which the store cannot do (N7, the rest of finding 12).
- **Three new mechanisms need one more sentence each, or they misfire.** Any signed-in client
  can make the server start a new epoch by sending a large number (N5). Two lost answers to
  `pull` in a row can sign an honest device out (N6). The device that is to repeat a removal
  after a restore holds no record of the removal (N2).

The check is much stronger than it was: it now fails for a dropped change, a row left deleted on
one device, a missing conflict and a dropped first loser. It does not look at authors, held
snippets, precedence or who may see what, so the wrong outcomes of findings 4, 5, 9, 12 and 13
still pass; the design, the module and the test strategy say where that line is, the Resolution
says more than is true (N12).

### N1. After a restore, a lost edit can be replaced unseen — high, by reading; its second part unconfirmed

- Rules: D7, in a new epoch: "A row the device may write … that the server holds in an older
  revision, or does not hold while the device's revision is above `lost_above`, is queued
  again"; and for every resync: "writing every row whose revision is the local one or above".
  C18 gives the server's side for three cases, the third being "onto a row an ordinary write
  changed in the new epoch it is an ordinary stale write (C3)". D7 never sends that re-push,
  because a revision of the new epoch (above 2^40) is not older than any a device holds.
- Sequence, one account, devices A and B, snippet `r` at revision 40 on both:
  1. A backup is taken. B goes offline.
  2. A edits `r`: applied at revision 60, after the backup. A is in step.
  3. The database is restored and `begin_epoch` runs: `lost_above` is about 50.
  4. B comes online first. Its position is of the old epoch: it resyncs and finds everything as
     it holds it. Its user edits `r`, based on revision 40, which is what the server holds: an
     ordinary write, not stale, applied in the new epoch, no conflict.
  5. A comes online and resyncs. `r` is a row A may write; the server holds it in a revision
     above A's 60. It is not queued. The resync writes the server's row over A's.
- End: the edit of step 2 was acknowledged by the server, lost by the restore, and is now on no
  device, not in the history (the restored one never had it), in no conflict and in no list.
  B's write replaced it without having seen it, which is the case C3 exists for. It is in none
  of the eleven places of §1, and A showed nothing but "the server was restored".
- The same holds when the writer of step 4 is another member's device.
- Why high: it is a lost edit under the design's own definition, and §14 requires the simulation
  of task 4.4 to include "a restore of the server" with the eleven places as its oracle, so a
  run with this order fails, or 4.4 writes an exception of its own. It needs a restore and a
  device that was away during the lost span, which is why the first review rated the restore
  medium; C18's title, "devices give back what the server lost", is not met here.
- Second part, the threshold for rows the server lacks. D7 removes "like any other" a row the
  server does not hold whose revision is not above `lost_above`, and `lost_above` is "the
  restored value of `rev_seq`, which no revision in the backup exceeds". That it is not below a
  restored revision is what §11.6 has task 4.2 verify. The loss is in the other direction: every
  revision between the last one the backup holds and the restored counter was given out, in the
  old timeline, to a write the restore lost. Those are the transactions in flight at the
  restore point, as the first review said; and, by knowledge of Postgres and not run here
  (unconfirmed), more than a moment's worth: a sequence is written to the log some values ahead
  (32), so after a recovery it stands up to that many values past the last one handed out
  before the recovery point. A snippet created in such a revision is removed from every device
  that holds it.
- Fix: (1) in a new epoch, also queue as a re-push every writable row the device holds in a
  revision above `lost_above` and below the new epoch's `first_rev` when the server holds it in
  a revision of the new epoch. The server already answers it as a stale write: it wins, and a
  conflict offers the other version to both. (2) For a row the server lacks, do not rely on the
  counter alone: `epoch.restored_to` holds the latest `updated_at` of the backup, a row's
  `updated_at` is the server's clock, and a row written after that time was lost, not purged.
  (3) A scenario for each, and a sentence in §1 that a restore loses nothing a device still
  holds.

### N2. The removal a device is to repeat after a restore leaves nothing on the device — medium, by reading

- Rules: D7, "Where the device held a tombstone of such a row and the server shows it live, a
  change that took access away after the backup was lost: … the device makes it again by itself
  (`remove_member`, `leave_group`, `withdraw_invitation`, `set_member_role` from admin to
  member, `delete_group`)". §5.13: a membership is readable when "it is their own (also as a
  tombstone); or it is live and they are a member of the same group".
- S30, as corrected for low finding 22: "on Ines's device his membership is simply gone, because
  nobody reads another person's tombstone". S58, step 5: "It held the tombstone of m-tom in a
  revision the server no longer has". S58's own outcome states `m-tom` as absent on Ines's
  device after the second removal. Both cannot be true.
- Per call: `remove_member`, no tombstone on the remover's device. `withdraw_invitation`,
  invitations are not synced rows (§5.8). `delete_group`, the profile's tombstone is readable
  by nobody (§5.12) and the device removes the profile row with its own membership (D6).
  `set_member_role`, the row is live on both sides, in different roles. Only `leave_group`
  leaves a tombstone the device can read, its own.
- Consequence when task 4.4 builds what §5.13 allows: after a restore the owner's device finds
  a live membership it has no row for and takes it. Tom is a member again and stays one. §11.3
  ("until a device of an owner or admin has synced and made the removal again") and question 3
  of §13, which the owner is asked to decide on, promise otherwise.
- Fix: a device-local list of the account calls that took access away, written when the call is
  answered `ok` and kept for the days a backup can be old. D7 compares the list with what the
  restored server shows. Or let owners and admins read the tombstones of their group's
  memberships, and say what stands for an invitation and a role.

### N3. A file is still readable by its hash — medium, by reading (the rest of finding 9)

- Rules: §5.13, `attachment_blob`: "a snippet they can read has a live link to an attachment row
  with its profile and hash. Having written an attachment row with that hash is not enough."
  §4.3: an attachment row may be created with "`edit` on at least one folder of the profile", a
  link with "`edit` on the snippet's folder; the attachment is in the folder's profile".
- Sequence, in the state of S28 with the share "to change". Ines's private snippet uses a file
  with the hash H; the verified file is `P/H`.
  1. Tom pushes an attachment row `at9` in profile P with the hash H. Allowed. The result says
     `blob: missing`, as it should.
  2. Tom pushes a link from the shared snippet `s1` to `at9`. Allowed: he may change `s1`, and
     `at9` is in the folder's profile.
  3. A snippet Tom can read now has a live link to an attachment row with profile P and hash H.
     The policy on `attachment_blob` holds; the object `P/H` is his to download.
- He never uploads anything. §6.11 expects him to ("the member has proved that they hold the
  bytes, learned nothing, and can read the file once a snippet they can read links to it"), and
  §4.4 says his rows give him "no file they did not upload"; no rule makes the read wait for
  the upload. Whether step 3 succeeds also tells him whether Ines holds such a file.
- Why medium: as in the first review, he must know the hash, which mostly means he has the
  file. G14 and the sixth line of §4.5 fail as worded.
- Fix: an attachment row is backed when its creator could read the verified file at the time
  (then `attachment_upload_begin` answered `exists`) or has since committed an upload with that
  hash; `attachment_verified` sets the mark on the uploader's rows. The policies on
  `attachment_blob` and on the stored object count only links to backed rows. A scenario beside
  S28.

### N4. A revoked device can register again after 30 days — medium, by reading; the session's life checked in the documentation (the rest of finding 10)

- Rules: C25, "a revoked row is kept for 30 days, longer than any token of its session can
  live, so a revoked session cannot register again under another id"; §5.12, "a revoked device
  row is removed 30 days after it was revoked"; C25, "the session has no row, and the id has
  none …: the row is created". §11.6 on ending a session from the database: "Not needed.
  Revocation is the device row."
- Supabase's sessions guide: "refresh tokens never expire but can only be used once", and "by
  default, all sessions are active until the user signs out"; limits on a session's life need a
  paid plan, which §11.3 does not rely on. The sign-out guide has three scopes (all sessions,
  this one, all others), none for one other session.
- Sequence: Ines revokes her lost computer B from A. B is offline. `revoke_device` marks B's
  row; B's session stays in `auth.sessions`, with a refresh token that is still good. Had B come
  online in the next 30 days, it would have been told `device_revoked` and signed itself out.
  It is switched on on day 40: the token is refreshed, `hello` finds a session that exists and
  has no row, and a device id with no row, and registers B. It resyncs the account.
- An access token lives an hour; the claim of C25 is true for those only. "Sign out everywhere"
  ends the sessions themselves (§11.3) and is not affected.
- Fix: the daily job removes a revoked row only when its session is gone from `auth.sessions`
  (the functions' owner reads that table already). Or record revoked session ids in a table that
  is never purged; `session_ok()` and `hello` look there.

### N5. A client's number starts a new epoch — medium, by reading

- Rules: C18, "`enter` runs it by itself when a device proves that the server lost data: a
  `hello` whose `max_rev` is above what `rev_seq` ever gave out in the current epoch, or a
  position ahead of the feed's head". `begin_epoch` "moves `rev_seq` 2^40 further, … empties
  the feeds and forgets the devices' position tokens". The `max_rev` member of `hello` is new
  in the revision.
- Neither is proof. A changed client that is signed in to any account sends `max_rev` as a
  large number. Every device of every account is then answered `reset_required: epoch` and
  reads everything it may read again; the rate limit allows ten `hello` calls a minute per
  device. I found no lost edit in it: the devices compare row by row and find nothing to send.
- G4: "none of them returns a fact about anyone but the caller or changes anything but the
  caller's device row and rate counters". `enter` is a gate helper that `authenticated` may
  execute, and it changes `server_state`, `epoch`, the counter, every feed and every device
  row. The first review's finding 16 said G4 could not pass as worded; reworded, it still
  cannot.
- Fix: the net does not change shared state on a claim. A device that reports more than the
  server knows is answered with a code that stops its sync and keeps its outbox, and the
  operator is alerted and runs `begin_epoch`. If an automatic net is wanted, let the server
  detect the restore itself, from a mark kept outside the database.

### N6. What "the last two positions" are after a repeat — medium, by reading

- Rules: C25, "The server keeps the last two it issued to the device. A call that presents the
  latest one is the normal case. One that presents the one before it is a repeat after an
  answer that did not arrive, and is answered again. A call that presents any other position of
  the current epoch is answered `device_conflict`." §5.3 says the same of the two columns.
- Sequence, one honest device at position P0:
  1. `pull` after P0. The server issues P1; it holds P0 and P1. The answer is lost.
  2. `pull` after P0 again: the one before, accepted. The server issues P2. Read as written,
     the last two it issued are P1 and P2. The answer is lost again.
  3. `pull` after P0: neither. `device_conflict`. The device makes a new id; `hello` answers
     `device_conflict` because "the session has a row under another id". The device signs out
     and asks the user to sign in again (D14).
- The same after step 1 when the store refuses the page twice (§6.9 expects three tries and a
  resync), when the agent stops before storing a page twice in a row, and when a resync is
  interrupted twice, since `start` of a snapshot is an issued position and the device still
  holds its old one. C25 also does not say which is judged first for a position that is both
  below the feed's floor and unknown: `reset_required` or `device_conflict`.
- S60 does not settle it: there the second installation syncs with a pull, a push and a pull,
  so both readings give its outcome.
- The other reading works: on a repeat the presented position stays "the one before" and only
  the latest is replaced. Then any number of lost answers is harmless, and a copy is still
  caught at the call after the other installation's next pull.
- Fix: say that in C25 and G22, with the rule for `start` and the order of the two answers. A
  scenario: two lost answers to `pull`.

### N7. Null rows of a tree that is revoked in the same page — medium, by reading (the rest of finding 12)

- Rules: §5.5, a `row` entry goes to "everyone who could read the row before the write or can
  read it after it"; §6.4, such a row is delivered as null when it is no longer readable; D3,
  "a null row removes the local row unless D2 holds", with "foreign keys checked at the end of
  the batch"; D6, visibility entries are handled "after the page's rows"; §5.4, the top of a
  tree that stops being readable while it exists gets `folder_revoked`.
- Sequence A, no unsent change needed: Ines moves the sub-folder `f1b`, with its snippets, out
  of the shared folder `f1`. The move writes `f1b`; its snippets are not written. Tom's feed
  gets `row` for `f1b`, delivered as null, and `folder_revoked` for `f1b`. His device applies
  the rows first: `f1b` is to be removed while its snippets are still there. The store's
  `snippet.folder_id` refers to the folder without a cascade, so the batch fails. Three tries,
  then a resync, whose access check purges the tree (D7). On every member's device, each time.
- Sequence B is S61 as written: Tom's `s1` has an unsent change, so its null row is skipped
  (D2), and `f1` cannot be removed. The same road. S61's note says only "the folder is
  revoked".
- It converges and nothing is lost: the purge keeps unsent changes. The cost is a full resync
  of each member's device for an ordinary action, and three refused pages in the log of an
  agent that "should not" see one.
- Fix: D3, a null row for a folder does what `PurgeFolder` does for it. Or §5.5: a user for
  whom the transaction revokes a tree gets no `row` entries for rows inside it. Either is one
  sentence; add sequence A as a scenario.

### What is still not checked

Nothing was run against Postgres or Supabase. The property N1's fix rests on, that a profile's
`head_rev` in a restored database is the last revision of that profile the backup holds, is
argued from the lock order of C24 and from a sequence without a cache, and is a verification
step for task 4.2 (§11.6), as are the four facts about sessions N4's fix needs. That a new
epoch's revisions lie above every earlier one rests on the server's clock not running backwards
between two restores and on revisions being drawn more slowly than a thousand per millisecond;
neither was measured. `server_behind` rests on the operator seeing a log line; the alert itself
is task 4.2's. Looked up again for this revision, and found as the review and the design state
them: the sign-out guide (three scopes, none for one other session; access tokens of an ended
session stay valid until they expire), the sessions guide (refresh tokens do not expire; a
session lasts until sign-out by default; the session id claim), `sequence.c` and the manual's
page on sequence functions. The scenarios S68 to S77 are right by reading and by the check as
far as it looks; the replay of task 4.4 derives them.
