# Phase 2 privacy and security review (task 2.8)

Date: 2026-11-19 · Commit reviewed: `85addaf` · Reviewer: independent, did not write the code

Scope: `iamb-platform`, `iamb-platform-windows`, `iamb-platform-macos`, `iamb-ipc`, `iamb-service`,
the soak and compatibility harnesses in `iamb-testkit`, and `iamb-core` where the service relies on
it (`Sensitive`, the keystroke buffer, suspension), judged against `docs/architecture.md` (§3, §4,
§6, §8), the decision records and `docs/test-strategy.md` §5. The review changed no file of the
tree and added this one. Probe programs, a mutated copy of the tree, memory dumps and logs were
kept outside the tree. The merge `e7c31aa` has the same tree as `85addaf`. Commit `0405223` (the
probe window of task 2.7) came while this was written and is not covered: it adds `unsafe` code
to both OS crates and features to their manifests, which the statements of §6 do not include.

What could be run here: everything on Linux against the mock platform (worker, supervisor, IPC,
soak harness). The Windows and macOS crates cannot run on this machine. Their system-independent
parts ran through their unit tests; the rest was read and type-checked for its target. Every
finding says whether it was demonstrated or found by reading.

## 1. Verdict

In the service's own code I found no path by which typed characters reach a file, a log line, an
IPC message or the network, and none by which form values or clipboard text reach a file or a log.
The service has no network code, and the measured canary scan is clean. Phase 2 is still not ready
to sign off: one finding is high and seven are medium, so the KPI "0 high or medium findings open"
is not met.

The high one is about where an expansion lands, not about a leak. With the default settings an
abbreviation ended with Tab or Enter is expanded after the application has acted on the key, so
the Backspaces and the text go into the next field, which in a login form is the password field
(finding 1). It is demonstrated on the mock and argued by reading for Windows and macOS; one lab
test, named in the finding, settles it.

Of the medium ones, two belong together. The scan that measures the privacy KPI looks only for a
whole canary as one string, so a build that writes every typed character to the log, one line per
key, passes it (finding 2). And the queue between the listener and the engine keeps the last 256
events in ordinary memory, characters typed into password fields included, which the scan cannot
see either (finding 3). The other five: no protection against operating-system crash dumps
(finding 4), keys that overtake a focus change (5), exclusions that silently do not apply (6), the
macOS clipboard not kept on the device (7), and a "no `std::net`" guard that network code passes
when it is imported in the nested form (8). Twelve findings are low.

## 3. Findings

Severity: high = typed text, form values or clipboard contents can reach disk, logs, the network,
another process or another user, or a secure field, exclusion or pause can be bypassed in normal
use; medium = the same only under unusual conditions, a deviation from the specification that
weakens a privacy rule, or a privacy test that cannot fail; low = hardening, documentation,
clarity. Status says whether I reproduced it.

### 1. An abbreviation ended with Tab or Enter is expanded in the field the key moved to, which can be a password field — high, demonstrated on the mock; by reading on Windows and macOS

- Where: `crates/iamb-core/src/matcher.rs:92-94` (Enter and Tab are in the default delimiter
  set), `crates/iamb-core/src/model.rs:663-665` (delimiter mode is the default trigger),
  `crates/iamb-core/src/engine.rs:613-623` and `:969` (they trigger, and the key is pressed again
  after the expansion);
  `crates/iamb-service/src/worker/engine.rs:309-311` and `crates/iamb-platform/src/handoff.rs:274`
  (a focus change cancels only until the start marker has come back);
  `crates/iamb-platform-windows/src/injector/run.rs:122-135` and
  `crates/iamb-platform-macos/src/injector/run.rs:149-168` (after that every step is sent, wherever
  the focus is).
- Rule: §4.6 names a focus change among the events that cancel an expansion and adds "The 2.8
  privacy review checks this"; §8 rule 7 and ADR-0012; the compatibility matrix expects that
  nothing expands in a password field (W19, W20, M19, M20).
- What: the listener never holds a key back (ADR-0010), so the application gets the real Tab or
  Enter first and acts on it: the next field takes the focus, a dialog closes, a message is sent.
  Iamb's Backspaces, text and second key press are queued behind that key and arrive in whatever
  has the focus by then. The service can only cancel if the focus notification reaches the engine
  thread before the injector's start marker has come back through the listener, which takes "well
  under a millisecond" (`handoff.rs:91`). A notification is raised by the application after it
  handled the key and then crosses three threads; browser engines raise theirs from their
  accessibility layer. The injectors do not look at the focus. Any trigger has this gap when a
  window takes the focus in that moment; with Tab and Enter the key itself causes the move.
- Shown by (mock, 300 rounds per case; the application's reaction is modelled by moving the focus
  to a password window right after the trigger key; Tab and a space as trigger in two runs, Enter
  in one):
  - With the mock's immediate notification the expansion was typed into the password field in 2
    to 121 rounds, depending on key and run; nearly all the others were cancelled.
  - With the notification passed through one more thread in the probe: 93 to 252.
  - Held back there by 0.1 ms, 0.3 ms, 1 ms or 5 ms: 296 to 300, for each of the three keys.
  - Each time the field `hunter22` became `huntbe right back` plus the key: four characters of
    the password field were deleted first.
- Not shown: the two delays on Windows and macOS. The compatibility matrix uses immediate
  triggers only, so no real application has been tried with a delimiter trigger.
- Failure scenario: a login form. The user types the abbreviation of an e-mail address in the
  first field and presses Tab. The abbreviation stays there unexpanded; the password field loses
  one character more than the abbreviation is long, if a password manager had filled it in,
  receives the address, and Tab is pressed again. With Enter in a dialog, a chat or a terminal
  the abbreviation is sent as typed, and the expansion with a second Enter follows in whatever
  has the focus then, which can be an excluded application. A `{wait}` or a paste keeps that
  window open for as long as the injection lasts.
- Fix: an owner decision first, because §4.4 (Enter and Tab are delimiters) and ADR-0010 (no key
  is held back) cannot both hold for keys the application acts on.
  - Safest: take Enter and Tab out of the default delimiter set, and say what they do in forms
    where a user turns them on.
  - Otherwise, for these two triggers: send nothing until the focus watcher has been quiet for a
    set time after the key, and cancel with a diagnostic when it reported anything. That costs a
    delay and still loses to a late notification. The stamp of finding 5 catches a change of
    window, not a change of field.
  - Either way, let the injector stop between steps when the focus has changed since the start
    marker.
  - Lab, task 2.7, before anything else: give the password pages (W20, M20) a text field before
    the password field, type a delimiter abbreviation and Tab in it, 50 times. Expected: nothing
    is typed or deleted in the password field. If the cancel wins there nearly always, this
    finding is medium.

### 2. The canary scan and the log test cannot see a build that logs every key — medium, demonstrated

- Where: `crates/iamb-testkit/src/soak/canary.rs:186-224` (the patterns),
  `crates/iamb-service/tests/log_scan.rs:81-86`.
- What: both search for a whole canary as one string (the scan in UTF-8, UTF-16LE and Base64 of
  the two; the test in UTF-8). A leak that writes one character per record is the most likely
  accident in this code (the engine thread handles one `Char` at a time) and is invisible to them.
  So is every form typed text has inside the worker: the buffer, the hand-off and the queue all
  hold `char`, which is UTF-32.
- Shown by:
  - In a copy of the tree I added one line to `EngineThread::on_key` that logs each typed
    character (`key 'x' seq n`). `cargo test -p iamb-service --test log_scan --test end_to_end`:
    18 of 18 pass. A 40-second soak of that build: PASS, "0 hits in 13 files", while
    `logs/worker.log` held 2,572 such lines. Joining them gives all 10 canaries back, those typed
    in the password field, the excluded app and under pause included.
  - The same canary planted in 16 forms, one file each: found as UTF-8, UTF-16LE and Base64; not
    found as a UTF-32 array, UTF-16BE, the debug form of a character slice (`['q', 'z', …]`), the
    debug form of bytes (`[113, 122, …]`), one key per log line, hex, upper case, percent
    encoding, JSON `\u` escapes, split over two lines, reversed, compressed, or one character
    per 96-byte record (the shape of finding 3).
  - A core file of the worker written right after a canary round (finding 4) holds all five
    canaries in the engine queue. `iamb-soak scan` on it reports one hit, a UTF-8 copy. Only the
    harness's control endpoint and the mock's text field hold typed text as UTF-8; the service
    handles it as `char`.
- Why it matters: the phase KPI is measured by this scan. As built it proves "no whole canary in a
  file", not "no typed key in a file".
- Fix: type a second kind of canary made of characters that occur nowhere else in a run (for
  example 16 letters of one script the fixture library, the logs and the protocol never use; check
  before the run that the scanned places hold none), and count every single occurrence of any of
  them, in UTF-8, UTF-16 and UTF-32, both byte orders, and as `\u` escapes. Keep the present
  canaries for whole-string forms and add UTF-32LE. Make `canary-scanner-control` plant each shape
  in a temporary file and require a hit for each. Give `tests/log_scan.rs` the same
  single-character rule.

### 3. The engine queue keeps the last 256 events, typed characters included, in unlocked memory that is never cleared — medium, demonstrated

- Where: `crates/iamb-service/src/worker/mod.rs:538` (`sync_channel::<EngineMsg>(256)`),
  `:458-467` (the listener's sink), `crates/iamb-platform/src/listener.rs:34`.
- Rule: §8 rule 1, "typed characters exist in exactly two places, both in locked memory"; §4.6
  rejects a copy on the hook thread because it "would have to hold every key all the time,
  including keys the engine drops in secure fields". The queue is that copy.
- What: every `ListenerEvent::Char` crosses a bounded standard-library channel. Its 256 slots (96
  bytes each, about 24 KB of ordinary heap) are neither locked nor overwritten when a message is
  taken out. The listener cannot know the engine is suspended, so keys typed into password fields,
  excluded apps and under pause go through it like any others.
- Shown by: a probe that runs the worker in-process on the mock and reads its own memory.
  - Password field focused, `GetStatus` says suspended, 16-character canary typed: the two locked
    regions (280 and 256 bytes) hold nothing, as designed. Elsewhere in writable memory all 16
    characters stand in typed order, one every 96 bytes, each next to its sequence number.
  - After 5 seconds idle (10 heartbeats): still all 16. After 230 more key events: all 16. They go
    between 236 and 256 more events; 3 of them survive beyond that, because a slot reused by a
    message of another kind keeps the old character.
  - In the soak worker, about one second after a canary round: all five canaries of the round, 16
    of 16 characters each (15 for one).
- Failure scenario: the user types a password and stops. The password stays in the worker's heap
  until 256 more keys, clicks or focus changes have happened: over a lunch break, into a
  hibernation image, into swap under memory pressure, or into a crash dump (finding 4).
- Fix: give key events a queue of the service's own: one fixed allocation, locked with the buffer
  and the hand-off, whose `pop` overwrites the slot (a `Char` slot with a zero character), and
  cleared at worker stop. Then name it in §8 rule 1 as the third place. Optional, on top: let the
  sink read an "engine suspended" flag and send characters without their value while it is set.
  Add a test that reads the queue's memory after a pop, as the probe did.

### 4. Nothing protects the worker's memory from operating-system crash dumps — medium, by reading (demonstrated on Linux)

- Where: `Cargo.toml:27` (`panic = "abort"` for release), `crates/iamb-service/src/main.rs:117-128`
  (the panic hook logs the location, then the process aborts). No code in the service or the OS
  crates deals with crash reporting; the Windows bindings do not enable the error-reporting
  namespace.
- Rule: §8 rule 9, "each process writes crash reports locally without heap contents and opts out
  of the operating system's own crash-dump collection where the OS allows".
- What: neither half exists. Because release panics abort, every Rust panic in the worker ends as
  an abnormal termination that the system's crash reporter handles in its own way.
- Shown by: soak worker with core files allowed (`ulimit -c unlimited`), `SIGABRT` right after a
  canary round: a 27.6 MB core file is written to the worker's working directory, and it holds
  all five canaries of the round in the queue of finding 3. The soak's own scan does not look
  there and reports 0 hits. On Windows and macOS the equivalent is the system's error reporting,
  which this machine cannot run.
- Fix: at worker start, on Windows switch off error reporting for the process (`SetErrorMode`,
  `WerSetFlags` with the no-heap flag, or `WerAddExcludedApplication`); on macOS catch the fatal
  signals, write the local heap-free report and leave with `_exit`; on Linux set the core limit
  to 0. In the panic hook, leave with an exit status the supervisor restarts on, not with an
  abort, so that a Rust panic is never an operating-system crash. Write the local report (thread,
  location, version) that rule 9 describes. Add the crash-dump directories to the lab scan list
  by name.

### 5. A key typed right after the focus moved is handled as typed in the previous field — medium, demonstrated on the mock; by reading on Windows and macOS

- Where: `crates/iamb-service/src/worker/mod.rs:608-615`: keys go from the hook straight into the
  engine queue; a focus change goes from the OS watcher to the focus thread
  (`worker/threads.rs:38-73`) and only then into the queue. Nothing ties a key to the window it was
  typed in.
- Rule: §8 rule 7, "secure fields … suspend the engine before a character is stored"; ADR-0012.
- What: until `FocusChanged` has reached the engine thread, the engine still has the verdict of
  the previous field. Keys typed into the new window in that time are stored, matched and can
  expand there.
- Shown by: `brb` typed in an ordinary field, focus moved to a password field, a space typed at
  once. In 105 of 300 rounds the engine matched `brb `; in 5 of them the deletion and the
  expansion were typed into the password field. With 50 µs between focus and key: 0 of 300. On the
  mock the window is one thread wake-up. On Windows the focus event is an out-of-context window
  event that the watcher thread receives later, and on macOS a notification through two run
  loops, so the window there is that delivery time; I could not measure it.
- Failure scenario: a tool that types a user name, Tab and a password a few milliseconds apart, or
  a dialog that takes the focus while the user types. The first characters in the password field
  are buffered and matched; an abbreviation among them expands there and names its snippet in the
  diagnostics. Nothing reaches disk; rule 7 is broken for that moment.
- Why the tests are green: the service tests and the soak wait for the engine after every focus
  change (`tests/end_to_end.rs:112`, `iamb-testkit/src/soak/host.rs:150`).
- Fix: let the listener say where a key went. The Windows hook already reads the foreground
  window for every key (`listener/pipeline.rs:463`). On macOS an event carries its target process
  once the system has routed it (`kCGEventTargetUnixProcessID`); whether the tap's place in the
  stream sees it has to be tried on a Mac. Carry that with the event, and let the engine thread
  compare it with the last focus change it delivered: on a mismatch, call `handoff.disturb()` and
  deliver `SecureState(Unknown)` first, so the engine is suspended until the focus thread has
  caught up. A field change inside one window stays as it is today; record that as a limit. Add a
  test that types without waiting. Finding 1 is the same lag from the other side: there the
  expansion, not a key, arrives in the new field.

### 6. An exclusion with another spelling is accepted and never applies — medium, demonstrated

- Where: `crates/iamb-service/src/library.rs:49-51` (exact string comparison),
  `crates/iamb-service/src/worker/handlers.rs:315-341` (`PutExclusion` stores what it is given).
- What: the Windows watcher reports the executable's file name in lower case
  (`focus/identity.rs`); macOS reports the bundle identifier as the application spells it. An
  exclusion stored in any other case never matches, and nothing says so.
- Shown by: `PutExclusion("Org.Example.Editor")` answers `done`; typing `brb ` in
  `org.example.editor` expands; no `suspended_excluded_app` entry appears.
- Failure scenario: the settings screen of Phase 3 passes `MyBank.exe` the way the file system
  spells it. The user sees the app in the exclusion list, and Iamb keeps buffering and expanding
  there. The exclusion list is the stated remedy for every detection limit (finding 17), so it
  must not fail open. `docs/compatibility-run.md` warns about the spelling for the manual route;
  the service does not.
- Fix: one normalising function used on write and on compare (lower case on Windows, also
  stripping a path; ASCII case-insensitive for bundle identifiers), a migration for stored rows,
  and `PutExclusion` answering with the identifier it stored.

### 7. macOS: pasted content and the restored clipboard are not kept on this device — medium, by reading

- Where: `crates/iamb-platform-macos/src/clipboard/mac.rs:68` (`clearContents` for every write and
  every restore), `clipboard/layout.rs:162-207` (only the two marker types of clipboard managers
  are added).
- Rule: §8 rule 8, "marked so that clipboard history and cloud clipboard services skip it". The
  Windows code sets all three markers, the cloud one included (`clipboard/formats.rs`).
- What: the system's own cross-device clipboard is not told anything. `NSPasteboard` has an option
  for it (`prepareForNewContents` with "current host only"); the code never uses it.
- Failure scenario: (a) a long expansion with form values is offered to the user's other devices
  while it is on the pasteboard. (b) The user copies a password from an app that marked it
  device-only, then triggers a pasted expansion: the restore writes the password back as ordinary
  content, which the other devices can now fetch. The restore also makes Iamb the owner and moves
  the change count, so an owner that clears its copy "if unchanged" no longer clears it (both
  systems).
- Fix: write the transient content with the device-only option. Restore with it as well when the
  snapshot carried a concealed or transient marker (or always; an owner decision). State the
  ownership change as a limit in the clipboard docs. Check on a Mac with a second device.

### 8. The `std::net` guard passes network code written with a nested import — medium, demonstrated

- Where: `crates/iamb-service/tests/no_network.rs:52-77`, `.github/workflows/ci.yml`.
- Rule: §2 and ADR-0008: "a lint forbids `std::net` in `iamb-service`, `iamb-ipc`, `iamb-store`
  and the platform crates"; §8 rule 5.
- What: the guard is not a lint. It is a test that searches the text of two crates for the string
  `std::net`. `use std::{io, net::TcpStream};` does not contain that string. The other four crates
  §2 names are not searched. The crate deny list cannot help, because this is the standard
  library. CI also has no step that builds the release binary with `-p iamb-service` alone
  (check 4 of ADR-0008), and nothing covers the socket functions of `libc`, which the macOS crate
  links.
- Shown by: in a copy of the tree, a function in `iamb-service` that imports `TcpStream` that way
  and connects. `cargo test -p iamb-service --test no_network`: 2 of 2 pass; the manifest guards
  of `iamb-platform` pass.
- Today's code is clean (§6); the finding is that the promise "checked in CI" does not hold for
  the standard library.
- Fix: a `clippy.toml` with `disallowed-types` and `disallowed-methods` for `std::net` and the
  `libc` socket calls, applied to all six crates; the release build step; and a check of the built
  binary's imports on each OS (no resolver or address functions, as §2 of this review did by
  hand).

### 9. §8 rule 1 does not describe what the code holds — low, demonstrated in part

- Where: `docs/architecture.md` §8 rule 1; `iamb-platform-windows/src/listener/deadkey.rs:400`
  (pending dead character), `listener/pipeline.rs:225` (half of a surrogate pair);
  `iamb-platform-macos/src/listener/translate.rs:173` (dead-key state);
  `crates/iamb-service/src/worker/engine.rs:288`.
- What: (a) the listeners hold one pending accent, and on Windows one half character, in ordinary
  thread memory. The accent is overwritten when replaced (`deadkey.rs:457`); the half surrogate is
  only taken (`pipeline.rs:414`); neither is cleared when the listener stops. One character at
  most, so no real exposure, but rule 1 says "exactly two places, both locked". (b) The hand-off
  also captures keys typed under pause when a palette pick or form submit is in flight: with pause
  on, a pick, and two keys typed before the start marker, the injector log shows `DeleteBack(2)`,
  `Retype(2)`. That is needed for a correct result, but §4.1 says characters typed while suspended
  are dropped unstored.
- Fix: rewrite rule 1 to list every place (after finding 3: queue, buffer, hand-off, the
  listener's one pending character) and say that the hand-off also runs for explicit requests
  under pause. Overwrite the half surrogate when taken and both values on stop.

### 10. The role is whatever the client says, and its version string is logged whole — low, demonstrated

- Where: `crates/iamb-ipc/src/server.rs:172`, `crates/iamb-service/src/worker/ipc.rs:166-169`.
- What: (a) one verified peer may open connections as `sync`, `cli` and `ui`. ADR-0006 promises
  that "a sync agent bug cannot read diagnostics or pause the engine"; that holds for a bug, not
  for a sync agent that was taken over from the network, which can say `ui` and receive
  `FormRequested` with the last form values, change exclusions and type snippets. (b)
  `client_version` is client text of up to 8 MB and goes into the log: a hello with a
  300,006-byte version grew `worker.log` by 300,375 bytes, and three hellos with a 1.1 MB version
  removed every earlier line from the five kept files (one file then holds 1.1 MB, over the 1 MB
  limit of §3.3).
- Fix: in release builds derive the allowed role from the verified executable (the sync binary may
  only be `sync`). Log at most 32 characters of the version, from a fixed alphabet.

### 11. The "installed binary" check is weaker than §6.1 says — low, by reading

- Where: `crates/iamb-platform-windows/src/endpoint.rs:252-301`,
  `crates/iamb-platform-macos/src/endpoint.rs:105-137` and `:148-201`.
- What: Windows accepts any executable in Iamb's directory with a valid signature from any
  publisher; with a per-user installation that directory is writable by the user's own programs.
  macOS identifies the peer by process id, which a process can change under the check by
  replacing its image while a child keeps the socket. The macOS check also compares the peer with
  the service's own designated requirement, which names the service's identifier, so as far as I
  can tell it will refuse the UI host and the command-line tool once builds are signed. The macOS
  check does not pass the flag that forbids network access (`kSecCSNoNetworkAccess`); the comment
  beside it says no network access is requested, which is not the same. Windows switches
  revocation checks off and limits retrieval to the local cache; whether the system's automatic
  root-list update can still go out during `WinVerifyTrust` belongs in the packet capture.
- Scope: same-user malware is outside the threat model (§8), so this is hardening. It matters
  because §6.1 presents the check as a boundary.
- Fix: compare the peer's signer with the running executable's signer on Windows; build the macOS
  requirement from the team identifier and identify the peer by audit token; set the no-network
  flag on macOS; say in §6.1 what the check does not stop. Test with signed builds in Phase 5.

### 12. Windows: another local user can keep the worker from starting — low, by reading

- Where: `crates/iamb-platform-windows/src/endpoint.rs:567-582`,
  `crates/iamb-service/src/worker/mod.rs:533-535`.
- What: the pipe name is public (`iamb-service-<user SID>`). Whoever creates it first owns it; the
  worker then fails with `EndpointInUse` and exits, and the supervisor retries every 30 seconds for
  ever. No data is exposed (clients verify the server and refuse), but expansion stops, although
  §3 says plain-text expansion needs neither of the other processes.
- Fix: start the worker without the endpoint when the name is taken, retry the bind, and show the
  state; or decide that this is accepted and say so in ADR-0006.

### 13. Form values are not cleared on screen lock or sign-out, and are dropped, not overwritten — low, by reading

- Where: `crates/iamb-service/src/worker/mod.rs:700-703` (`Worker::forget_form_values` has no
  caller), `worker/engine.rs:168-189` (only the 30-minute expiry is wired).
- Rule: §8 rule 2 through §4.5, "cleared after 30 minutes without use, on screen lock, on
  sign-out and on restart".
- What: no platform trait reports a lock or a sign-out, so two of the four triggers do not exist.
  The same holds for `TypedHandoff::clear` "on screen lock". Sign-out ends the user's processes,
  so the one missing in practice is the screen lock: values stay up to 30 minutes behind a locked
  screen. When values are forgotten, and when a clipboard snapshot is dropped after a restore, the
  bytes stay in freed memory.
- Why low: a code comment defers the trigger to task 3.x, and no form exists before Phase 3. It
  is a deviation from rule 2 the day a form ships without it, so it needs an owner now.
- Fix: add a session-event source to the platform traits and record it in §5 and in the plan,
  call `forget_form_values` and `handoff.clear` from it, and overwrite form values and snapshot
  bytes before freeing them (the Windows clipboard code already has `wipe`).

### 14. An incomplete clipboard snapshot is pasted over all the same — low, by reading

- Where: `crates/iamb-platform-windows/src/clipboard/paste.rs:86-124`,
  `crates/iamb-platform-macos/src/clipboard/paste.rs:26-45`; `ClipboardSnapshot::is_complete` is
  read only by tests.
- What: formats that cannot be copied (handles, formats over 64 MB, data the owner did not
  deliver, anything after the 500 ms limit) are left out. The paste goes ahead and the restore
  puts back the rest, so part of what the user had copied is gone, without a diagnostic. Rule 8
  says the previous content is restored.
- Fix: when the snapshot is incomplete, type the text with keys, or refuse the paste with a
  diagnostic.

### 15. macOS focus tracker: an element learned by reading can hide a move into another field — low, by reading

- Where: `crates/iamb-platform-macos/src/focus/watcher.rs:364-386` and `:396-421`,
  `focus/track.rs:136-164`.
- What: after a report the watcher reads which element has the focus and remembers it, so that
  the notification for the same element is not reported twice. The service inspects the field at
  about the same time. If the focus moves between the two reads, the watcher learns the new
  element, drops its notification as a repeat, and the engine keeps the verdict of the old one.
- Limit: secure keyboard entry covers ordinary password fields (no key reaches the tap, and the
  flag is seen at the next look within 100 to 500 ms), so this needs a password field that does
  not switch it on, and a move within the watcher's first moments in an application.
- Also: neither system checks that its focus watcher is still alive, as the listener's self-test
  does; if a watcher stops, the last verdict stays. The key stamp of finding 5 would close that.
- Fix: report once more after an element was learned by reading, or report the first notification
  after such a read even when it names the same element.

### 16. macOS: typing in Iamb's own panels cannot be reported as `own_window` — low, by reading; decision needed before task 3.5

- Where: `crates/iamb-platform-macos/src/focus.rs:105-108`; `docs/architecture.md` §4.5, §6.2.
- What: the form and the palette are non-activating panels, so the frontmost application stays the
  target, the verdict stays `normal`, and what the user types into a form field or the palette
  would pass through the keystroke buffer and be matched. In a form a match is dropped with
  `form_open`, naming the snippet; in the palette it would expand into the search field. §4.5 says
  the focus thread reports `own_window` for the UI host; on macOS it cannot. §6.2 has no message
  with which the UI host could say that a panel has the keyboard.
- Fix: add that message (for example `SetPanelActive(bool)`, UI role only) and suspend on it, or
  suspend from `FormRequested` and `PaletteRequested` until the answer. Record it in ADR-0013.

### 17. The limits of secure-field and input-method detection are recorded only in code comments — low

- Where: `crates/iamb-platform-windows/src/focus.rs:80-117`,
  `crates/iamb-platform-macos/src/focus.rs:89-108`, `docs/compatibility-run.md`.
- What: a password typed at a terminal prompt is not detected on Windows, nor on macOS unless the
  terminal has secure keyboard entry switched on: it is buffered and an abbreviation in it
  expands. On Windows a window that describes nothing about its fields is `normal`, not
  `unknown`. Both are reasoned choices, but §4.1 and rule 7 read as if anything that cannot be
  inspected were suspended.
- The same holds for input methods (rule 7 names composition). Windows
  (`listener/ime.rs:22-33`): a method on an ordinary layout handle is not recognised, and a
  switch the listener does not notice is seen one key late. macOS (`listener/inputs.rs:6-31`):
  the layout in use is published by the main thread, so a key typed right after a switch is still
  read with the old one, and the press-and-hold accent menu is invisible. Both fail closed
  otherwise: on Windows an unanswered question counts as composing; on macOS no key is text
  while an input method is selected or no layout is known.
- Fix: a decision record that names the limits and the remedy (exclusion list, pause), a line in
  §8 rule 7, and a place in the privacy documentation.

### 18. Missing tests for privacy behaviour — low, demonstrated

- Removing all three `handoff.disturb()` calls of the engine thread (focus change, verdict, pause)
  fails no test of `iamb-service` and no soak rule. The mock can script keys before the start
  marker, but not a focus change, verdict or pause there.
- No test types without waiting for the engine after a focus change (finding 5), and none moves
  the focus between a trigger and its injection (finding 1). The mock reports a focus change at
  once, which hides both; an option for a late notification, as the probe used, would show them.
- No test reads memory after typing; the probe of finding 3 did it without `unsafe`, through
  `/proc/self/mem`, and can become a Linux test. The same technique closes the recorded gap
  "zero on drop is not tested" for the buffer and the hand-off.
- The secure-field code of the two OS crates is tested only where a desktop is present; its
  results belong in the lab record of task 2.7.

### 19. Two log lines print a store error whole — low, by reading

- Where: `crates/iamb-service/src/worker/store.rs:147` and `:186`.
- What: `StoreError::InvalidData` can quote a stored value. That is library content, not typed
  text, but the log's own rule is names, sizes, counts, ids and codes. Fix: log the error's kind.

### 20. Smaller points — low

- `run/supervisor.lock` is created with mode `0644` (`supervisor.rs:114-126`); it sits in a `0700`
  directory and is empty.
- On Windows the data root, logs and library get the permissions of their parent
  (`paths.rs:109`). The default under `%APPDATA%` is private; a root chosen with `--data-dir` or
  `IAMB_DATA_DIR` elsewhere is not tightened.
- The soak does not scan the worker's working directory, where Linux writes core files.
- `report.json` has `git_sha: null` when the harness runs outside the repository.
- `iamb-platform-windows/src/endpoint.rs:337` (`finish`) holds a shared reference to the
  `OVERLAPPED` structure while the system completes the operation and writes its status fields.
  A shared reference promises that the memory does not change. The code reads only `hEvent`
  through it, so nothing goes wrong in the built program; pass a raw pointer, as `accept` does a
  few lines below. By reading.

## 4. Where typed text lives

| Place | Holds | Locked | Lives until | Cleared |
| --- | --- | --- | --- | --- |
| Hook or tap callback (stack) | One key's code and characters | No | The callback returns | Overwritten by later calls |
| Windows listener state | One pending accent; one half of a character another program injects | No | The next key that uses it, a layout change, lost events | Accent: zero when replaced. Half: taken only. Neither on stop (finding 9) |
| macOS listener state | A 32-bit dead-key state (which accent is pending) | No | The next translated key or a reset | Overwritten |
| Engine queue | Every character, in every context, with its sequence number | No | 256 later messages; without typing, indefinitely | Never (finding 3) |
| Engine thread stack | The message being handled | No | The next message | Overwritten |
| Keystroke buffer | At most 66 characters, ordinary fields only | Yes (280 bytes) | Boundary, focus change, verdict, pause, composition, overflow, expansion; Backspace frees one slot | Zeros; read back from memory: 5 letters present, then all zero after a click |
| Typed-characters hand-off | At most 64 characters typed after a trigger | Yes (256 bytes) | End marker, `finish`, cancel, re-arm, worker stop | Zeros (unit tests read the storage) |
| Injector batch | The characters to type again | No | The send call returns | Zeros: Windows on drop, sized so it never reallocates; macOS a stack array and fixed chunks, both zeroed |
| Delimiter in `TypeText` | The one delimiter typed | No | The injection ends | Dropped |

## 6. Checked, no findings

- Logs: every call site of the logger in the service. Lines hold fixed text, message names, sizes,
  durations, counts, ids, process ids and error codes. The 3-minute run's `worker.log` had 27
  distinct line shapes, none with content. The panic hook logs thread and location only and
  replaces the default hook; nothing prints a panic message.
- `Debug` and `Display`: `Sensitive` and `KeyBuffer` have none; `Secret` prints `<redacted>`;
  `ListenerEvent`, `Event`, `Action`, `InjectionStep`, `ClipboardContent`, `ClipboardFlavour`,
  `TypedHandoff`, `FormValues`, the IPC bodies and the Windows and macOS key types print shapes,
  lengths or names. `PlatformError`, `FrameError`, `DecodeError` and `IpcError` carry static text
  and numbers.
- IPC: no request returns the buffer or the hand-off; `DryRun` uses a fresh engine and never
  reads the real clipboard; the message log sees name, size, duration and error code; frames are
  limited to 8 MB in both directions; role checks happen before the handler; at most 8 clients;
  malformed and oversized frames are answered without quoting them. The IPC tap of the soak
  (57,493 bytes, every frame) held no canary.
- Local access: Unix socket `0600` in a `0700` directory owned by the user, exclusive bind behind
  a lock file, stale sockets removed only when nothing answers. After the run: data root, `logs`
  and `run` `0700`; `library.db`, logs and locks `0600` (one lock file excepted, finding 20).
  Windows pipe: first instance only, access for the user's SID only, remote clients rejected,
  clients connect at identification level, both sides identify the peer before the first byte (by
  reading). Single instance: `supervisor.lock`, then the store lock and the endpoint.
- Secure fields, exclusions, pause, own windows, unknown answers with the mock: nothing typed
  there is stored in the two locked regions or expands (read from memory, and by the service
  tests and 15 canaries), once the engine has heard of the focus change (findings 1 and 5 are
  about the time before). A verdict is always for the change before it; a verdict for a window
  that lost the focus is `unknown` on both systems (inspection checks the front window before and
  after). The Windows watcher does not de-duplicate focus events. `SetTestField` cannot make a
  secure field normal.
- Suspension in the engine: `Char`, `Backspace` and `Boundary` do nothing while suspended; every
  focus, verdict, composition, pause and overflow event clears the buffer; explicit requests wait
  for the verdict.
- The hand-off, which §4.6 asks this review to check: it is written only by the thread that feeds
  the engine, for each event before the engine handles it (`worker/engine.rs:288`), and read only
  by the injector, inside `read`, after the start marker. While it captures, a boundary, a
  Backspace past the trigger, a 65th character, composition, overflow, a focus change, a verdict
  and pause cancel and zero it. A waiting dead key is reported as a boundary before the start
  marker on both systems (`listener/pipeline.rs:389-394`, `listener/core.rs:197-200`). It is
  zeroed on finish, re-arm, clear and drop, and its storage is locked. What does not hold is in
  findings 1 (a focus change after the start marker cancels nothing), 3 (the queue is a standing
  copy of every key) and 18 (the three `disturb` calls have no test in the service).
- Network: 47 packages, none on the deny list or a networking crate by my own reading; no
  `std::net` type in any of the six crates; Windows bindings limited to 18 namespaces, none for
  networking; macOS bindings with default features off; UI Automation is created in-process.
- `unsafe`, by reading: Windows hooks and message loops, `ToUnicodeEx` in the mode that leaves
  keyboard state alone, the layout-file reader (system directory only, bare file names), the
  UI Automation method tables (slots 8, 21 and 35 match the interface definition as far as I
  can check without the SDK), clipboard global memory, overlapped pipe I/O (every operation is
  awaited before its buffer is freed), token and SID reads, the registry calls of the login
  item, `VirtualLock`; macOS event tap and its callbacks (the state they point to outlives the
  tap; a panic cannot unwind into system frames), the run-loop signal shared between threads,
  the key translation on a private copy of the layout data, Accessibility reads limited to
  focused element, role and subrole, the hand-written Carbon declarations and the hotkey
  handler, the login-item and permission calls, `mlock`, peer credentials. Every `unsafe` block
  of the two crates was read (24 files, two of them tests); the other crates forbid `unsafe` and
  only mention the word. I found no missing safety comment (lint-enforced) and nothing unsound
  apart from the note on `finish` in finding 20.
- Clipboard, Windows: the three history and cloud markers on every transient write and every
  restore; restore on every path after the write; newer content from the user is left alone
  (sequence number, change count on macOS).
- Supervisor: no hooks, no user data, heartbeat over a pipe, the worker ends when the supervisor
  dies.
