## 1. Verdict

Phase 2's privacy gate cannot close yet: no high finding is open, but two medium items are.

- **Finding 5 is fixed on Windows and on the mock, not on macOS.** The macOS listener still
  reports a key without the window it went to, so there the engine handles a key typed right
  after a focus change with the verdict of the previous field, as the first review described.
  The fix commit lists this as "still open (low)"; nothing lowers it. It is the unfixed half of
  a medium finding.
- **N1 (new, the open part of finding 1).** The injectors' focus guard notes the focus only
  right before the start marker. A window that takes the focus between the trigger key and that
  moment still receives the whole expansion: on the mock, 299 to 300 of 300 rounds once the focus
  report is 0.1 ms late, with four characters of a password field deleted first, the same
  figures the first review measured. The guard stopped none of them.

The high part of finding 1 is fixed: Enter and Tab are no longer default delimiters, so with the
default settings no trigger key makes the application move the focus. Findings 2, 3, 4, 6, 7 and
8 are fixed, each with a test that fails when I revert the fix in the scratch copy. The key
queue held up under three threads (9 million keys, no event lost unannounced, out of order or
left in memory). The 2-minute soak passes with 0 canary hits, and the scan now fails on a build
that logs every key. I found no new high finding, one new medium (N1) and six new low ones, two
of them caused by the fixes: on macOS an application whose name has a space cannot be excluded
any more (N2), and on Windows a paste is refused while the clipboard holds a picture format,
which an ordinary copy from office programs is likely to leave there (N4).

The gate can close once N1 is fixed and the macOS half of finding 5 is fixed or accepted by the
owner in a decision record. Both are small: a prototype of the N1 fix (the request carries the
trigger's window, the injector refuses to start elsewhere; about 12 lines) brought the probe to
0 of 300 in every case.

### N1. The focus guard starts after the gap it should close — medium, demonstrated on the mock; by reading on Windows and macOS (the open part of finding 1)

- Where: `crates/iamb-platform/src/mock/mod.rs:1179`,
  `crates/iamb-platform-windows/src/injector/run.rs:110`,
  `crates/iamb-platform-macos/src/injector/run.rs:170` (each injector reads the guard's reference
  itself, right before its start marker); `crates/iamb-service/src/worker/engine.rs:527-530` (the
  request names the application for the strategy, nothing about the window);
  `docs/decisions/0026-enter-and-tab-not-default-delimiters.md:10`.
- What: the guard compares the focus before each batch with the focus the injector thread read a
  moment earlier. A change between the trigger key and that read is inside neither check: the
  service cancels only when the notification arrives before the start marker is back, and the
  guard starts from the new window. The key stamp of finding 5 helps only if a key is typed in
  the new window in that time.
- Shown by: the first review's probe, 300 rounds per case. `brb` and the trigger in an ordinary
  window; the focus moves to a password window holding `hunter22` right after the trigger key.

  | Trigger | Focus report | Typed into the password field | Cancelled by the service | Stopped by the guard |
  | --- | --- | --- | --- | --- |
  | Space | Immediate | 2 | 298 | 0 |
  | Space | 0.1 ms late | 299 | 1 | 0 |
  | Space | 1 ms late | 300 | 0 | 0 |
  | Space | 5 ms late | 300 | 0 | 0 |
  | Tab, added to the delimiters | Immediate | 4 | 296 | 0 |
  | Tab, added to the delimiters | 1 ms late | 300 | 0 | 0 |

  Each time the field became `huntbe right back` plus the trigger: four characters deleted, then
  every step and the end marker. The first review measured 2 to 121, then 296 to 300. Scripted
  (`script_at(BeforeStartMarker, …)` with the reports held), the injector log is `StartMarker,
  DeleteBack(4), TypeText, TypeText, EndMarker`.
- Why medium and not high: with Enter and Tab out of the default set, no default trigger makes
  the application move the focus. It takes another window that takes the focus within about a
  millisecond of a trigger key, the same kind of coincidence as finding 5. For a user who adds
  Tab or Enter it is the first review's high case unchanged; ADR-0026 item 2 leaves the warning
  to the settings screen.
- Not shown: Windows and macOS. On macOS a field with secure keyboard entry on should be safe,
  because the start marker cannot come back through the tap; an ordinary field in the new window
  is not.
- ADR-0026 item 3 says a trigger that loses the race "sends at most one step to the wrong place".
  In the rounds above every step went there. On Windows, by reading, one batch is the whole
  expansion, and keys queued behind a trigger the application has not handled yet follow it
  wherever it goes; the guard reads the focus before that.
- Fix: put the trigger's window in the request. The engine thread has it: the token of the last
  `FocusChanged` it delivered, which every key it accepted was compared with. Each injector then
  refuses to start (`Cancelled(FocusMoved)`, nothing sent) when the window in front is another
  one: the first two numbers of `keyboard_focus()` on Windows, the frontmost process on macOS.
  I tried this on the mock in the scratch copy: one field, one comparison before the start
  marker, about a dozen lines. All six cases gave 0 of 300 (3 to 300 stopped by the injector,
  the rest cancelled by the service as before). A move inside one window stays invisible where
  the window is all that is known: say so in ADR-0026 and correct item 3. Add the scripted case
  to `tests/focus_order.rs`.

### N2. macOS: an application whose name has a space, a `+` or a non-ASCII letter cannot be excluded — low, by reading; the rule itself run on Linux

- Where: `crates/iamb-service/src/library.rs:132-141` (the macOS rule accepts only letters,
  digits, `-`, `.` and `_`), `:327` (a stored row that does not pass is left out of the compare
  set); `crates/iamb-platform-macos/src/focus/identity.rs:44-56` (the inspector reports the
  bundle identifier as the application spells it, or the executable's file name for a program
  without one); `crates/iamb-service/tests/exclusions.rs:79` (the refusal is asserted).
- What: the rule's premise, "only letters, digits, `-`, `.` and `_` occur in one", holds for
  identifiers that follow the convention. As far as I know the system does not enforce it (I
  could not check that on a Mac), and an executable's file name, which the inspector falls back
  to, can hold any character.
- Shown by: `AppIdRule::MacBundle` called here. An identifier with spaces, `My Tool`,
  `com.example.app+beta` and one with `ä`: `normalise` answers `Err(Character)` and `key_of` a
  key that no stored exclusion can have. `com.apple.TextEdit`, `python3.12` and
  `qemu-system-x86_64` pass.
- Failure scenario: the settings screen passes the name the diagnostics show for such an
  application. `PutExclusion` answers `invalid`, "a character no application id of this system
  has". The user cannot exclude it; only the pause is left. A row for it that is already stored
  (an import, sync, an older build) is listed by `ListExclusions` and never applies; the worker
  logs a count. §8 says "an exclusion must never fail silently".
- Before the fix the exact spelling could be stored and did match.
- Fix: on macOS refuse only what cannot be reported at all (empty, a control character, `/`),
  and compare without regard to ASCII case. Test with the examples of the identity module.

## 5. How the fixes were tested, and what showed no problem

- **Key queue (finding 3).** Read: the sink sends the notice and fills the slot under the queue's
  lock, the engine thread takes the event under the same lock after the notice, nothing on the
  path allocates, and no other message of the engine channel carries a character. Stressed in
  the scratch copy, three runs: one thread delivers 3 million `Char` events, a second floods the
  channel with other messages, a third plays the engine. 581,000 to 704,000 events got through
  per run, between 427,000 and 595,000 `Overflow` notices. No notice came without its event, no
  event came out of order or with a wrong character, every gap in the sequence numbers was
  announced by `Overflow` first, and at the end the queue was empty with every slot zero.
- **Memory (finding 3).** A probe of my own on top of the tree's test: 16 different characters
  typed into a password field, then every writable mapping searched for each code point. None in
  the three locked regions. Elsewhere, outside the mock's own text field: the last character in
  32 places and the first in 3, the 14 in between nowhere. The copies are in anonymous mappings
  (stacks and heaps, which the worker shares with the mock in this process, so I cannot say
  whose they are). After 1.5 seconds idle and 40 clicks: 13 and 3. In an ordinary field the 16
  stand in the locked buffer and are gone after a click.
- **Key target (finding 5), by reading.** The Windows token and the hook's stamp are built from
  the same call and the same two numbers, also for an application in a system frame window: the
  frame's process is used for both, the inner one only for the name. Marker events carry no
  target, so a start marker is never dropped. The watcher reports on any event that finds
  another window in front, so a missed foreground event is made up for by the next focus event.
- **Crash handling (finding 4).** The report holds the process, version, system, time, process
