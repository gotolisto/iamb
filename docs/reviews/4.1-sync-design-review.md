## 1. Result

**5 high, 16 medium, 19 low.** The test of task 4.1 is met as written: 49 scenarios, each with a
stated outcome for the server and every device, and the check that counts them passes. The
design is not yet one that tasks 4.2 to 4.4 can build without deciding things themselves.

The frame holds up, and most of it is careful work: the server's order instead of clocks, writes
through functions with receipts, a feed that carries no content and is read through the reader's
policies, access entries shared by the policies and the feed, the rule that a pulled row never
replaces an unsent change, refused changes kept on the device. Apart from the race of finding 3,
I found no way for a stranger or a member who may only use a folder to read or write beyond §4,
and no way for a write by one account to appear under another's name on the server.

The high findings are of three kinds. Two are sequences in which a device moves its feed
position past a row it did not apply and then never sends or receives that row again: the two
devices of one account disagree for good, which is the Phase 4 gate (findings 1 and 2). One is a
decision the design leaves out and task 4.2 cannot avoid: what two requests that arrive together
may assume about each other (finding 3). Two are in the trust model for shared folders, where a
stated guarantee does not follow from the rules: a member who may change a shared folder can
take over an abbreviation of the folder owner's own private snippets (finding 4), and content
with key presses written by one person can become the reader's "own" without any review, through
the reader's own stale write, a copy, or a re-push (finding 5).

## 3. Details of the high and medium findings

### 1. A delete after an unacknowledged create is dropped — high, by reading

- Rule: D1, "A row that was created and deleted without ever being sent is not sent at all: its
  entries are dropped and the row removed." The store cannot know "ever sent": the outbox of
  §7.1 gains `op_id`, `cascade_of`, `blocked` and `repush_rev`, no mark that an entry was handed
  to the agent, and `OutboxRead` only returns. What the store can see is a local revision of 0.
- Sequence, one account, devices A and B:
  1. A creates `s` (entry e1: put, base 0).
  2. A pushes. The server commits `s` at revision R and writes the feed entries. The answer is
     lost and the agent stops before a repeat is answered (quit, crash, restart for an update).
  3. The user deletes `s` on A (entry e2: delete, base 0, because the local revision is still 0).
     It makes no difference whether this happens before or after step 2's stop.
  4. The agent starts and pulls. The feed holds `s` at R; `s` has outbox entries, so the answer
     is `shadowed` (D2) and the position moves past the entry.
  5. Push: `OutboxRead` builds the changes under D1. `s` was created and deleted and its
     revision is 0: the entries are dropped, the row is removed, nothing is sent.
- End: the server and B hold `s` live at R; A holds nothing and will not be told again. The
  delete is in none of the six places of §1 (I2), and A and B differ until somebody writes `s`
  (I1). D4 covers the case in which the answer does arrive; §6.9 covers the repeat by the same
  process; neither covers a new process.
- Fix: set a mark on an entry when `OutboxRead` hands it out, in the store. D1's drop applies
  only when no entry of the row has the mark. Otherwise the delete is sent with base 0; C5
  already answers `unchanged` when the server never saw the row. The general net is in
  finding 2.

### 2. Rows of a cascade get no answer — high, by reading

- Rule: §6.3, cascaded rows "are not sent as ops of their own" and the answer has "one result
  per op"; C6 deletes "every live folder and snippet below it as they are on the server at that
  moment"; D4 and D5 act on "the row of the answer".
- Sequence A (a move out of the folder), devices A and B of one account, folder `f1` with `s1`
  and `s2`, folder `g1`:
  1. A, offline, deletes `f1`. Locally `f1`, `s1` and `s2` are tombstones, with entries.
  2. B moves `s1` to `g1`: applied, revision R.
  3. A comes online and pulls: `s1` at R has an entry, so `shadowed`; the position moves on.
  4. A pushes the delete of `f1` with the cascade list `s1@5`, `s2@6`. The server deletes what
     is below `f1` now: `s2`. `s1` is in `g1` and stays live. Answer: `f1` `applied`.
  5. A removes the entries the change covered, those of `s1` included. The answer has no row
     for `s1`; the feed has nothing new for it.
- End: `s1` is live in `g1` on the server and on B, and deleted on A; after 30 days A purges it
  (D8). No conflict, nothing shown. Neither device's user chose this state.
- Sequence B (the folder's delete is refused): a member deletes a sub-folder offline; before
  the push the share is lowered to "use only". The answer for the folder is
  `rejected: forbidden` with the server's row, which D5 puts back. The cascaded rows are still
  tombstones on the device, live on the server, and no feed entry comes.
- Fix: the result of a folder delete lists, for each row of the cascade list, the row as the
  server has it now (or that it was deleted), and D4 and D5 apply each. A net that also closes
  finding 1: the store remembers every row answered `shadowed` with the revision it skipped;
  when the row's last entry is removed and its revision is still below that, the agent fetches
  the row (one small call, `rows(ids)`, through the policies). Scenario to add: "one device
  deletes a folder, the other moved a snippet out of it".

### 3. No rule for two requests at the same moment — high, by reading

- Rules: C1 takes "a row lock" on the row written; C15 locks the device's receipts; the feed
  locks one user's head at a time; C16 says the account calls lock the group's profile row.
  `push` is not said to lock anything a second request would also lock, and under the default
  isolation of Postgres each statement of a function sees what was committed when it began.
- Three interleavings, each of two transactions that both pass their checks:
  1. *Cycle.* P1 moves `fa` under `fb`; P2 moves `fb` under `fa`. Each finds the other folder
     at the top level (C8), both commit. S13 defines the outcome only when the requests arrive
     one after the other; D3's eight-step rule treats a cycle as something that lasts "a moment".
  2. *Live row under a deleted folder.* P1 deletes `f1` and cascades to what it sees; P2
     creates `s3` in `f1`, which it finds live. After both: `s3` is live inside a tombstone, with
     no conflict and no tombstone of its own (C6, C7 both assume the other went first). Devices
     show nothing of it; at the purge it is in the way of "children before parents" or goes
     with the folder, unrecorded.
  3. *Access for an ended share.* P1 (the owner) deletes the share of `f1`; `refresh_access`
     removes the entries of the tree it sees. P2 (a member, or the owner's other device) creates
     the sub-folder `f1x`; its `refresh_access` adds entries for the members from the share it
     still sees. After both, a member has an access entry for `f1x` and no share: G1 is broken,
     and every query as that member returns `f1x` and what is later put in it. The same holds
     for `remove_member` against a push into a group's folder.
- The feed's lock order ("in the order of the user ids") also cannot hold as written when the
  ops of one push write to different sets of users one after another; that only costs a
  deadlock and a retry, which C15 makes safe.
- Fix: state the order once and make it G-testable: receipts of the device; then, `FOR UPDATE`
  and in id order, the profile row of every profile the request touches (the owner's personal
  profile for its folders, and the group for a share or a group's folder); then the rows; then
  the feed heads in user order, collected for the whole request. Writes of one profile are then
  serial, which is cheap at this size, and the account calls already start at the same row.

### 4. An editor of a shared folder can take the owner's abbreviations — high, by reading

- Rules: D13 orders "first the snippets of the user's personal profile; then the other access
  roots …; inside one of these by `created_at` and then id", and concludes: "A snippet in a
  shared folder can therefore never take an abbreviation from one of the user's own." §11.3
  repeats it. That is true for the people a folder is shared *with*. For the person who shares
  it, the shared folder is in their personal profile (§4.2, ADR-0014), so the member's snippet
  and the owner's private one are "inside one of these". `created_at` is "what the creating
  device sent, but never later than the server's clock" (§5.1, C1): nothing bounds it below.
- Sequence: Ines's private folder holds `;iban`, created in March. She shares "Shop replies"
  with the family, to change. Tom's device creates in it a snippet `;iban` with one line of
  text and a creation time before March (a wrong clock is enough; S25 shows the mechanism
  between two honest devices and calls the result intended). The server does not compare
  abbreviations (C9) and keeps the time. On Ines's devices Tom's snippet holds `;iban`; hers
  "neither expands nor resolves" and is listed in library health. One line of plain text is
  not held (D10). Tom cannot see which abbreviations Ines has; he can guess the common ones.
- Without the old date the same happens when the two snippets were created without seeing each
  other (one of the devices was offline) and the member's is the older.
- Fix: inside the personal profile, snippets whose `content_by` is the signed-in user come
  first, the others after them; the order among the others uses a time the server sets when it
  first accepts the row. Correct D13's sentence and §11.3. Scenario to add.

### 5. The reader becomes the author of content they never approved — high, by reading

- Rules: C17 sets `content_by` to the caller "when the write changes the abbreviation, kind,
  body, trigger, case mode or word-start flag", that is, when they differ from the row being
  replaced. D10 holds a snippet only when `content_by` is not the signed-in user, and
  "whenever a revision is not held … those six fields are stored as `approved_content`". S40
  covers the case in which the pushed content equals the current row. Three cases in which it
  does not:
  1. *The reader's stale write.* `s1` in a folder shared to change. R1: Tom writes
     `{clipboard}{key name="enter"}` into the body; `content_by` Tom. Ines's device A pulls R1:
     held; the row on A carries Tom's content. R2: Jun, or Tom, changes the body again. Before
     A has pulled R2 (offline, or inside the seconds a sync takes) Ines changes the label on A.
     A pushes the whole row (C2): Tom's content of R1 with her label, base R1. It is stale and
     applied (C3); its six fields differ from R2, so `content_by` becomes Ines. On A and on her
     other devices the content is now her own: not held, stored as approved, and `;wtrack`
     reads the clipboard and presses Enter. A conflict is recorded; a conflict holds nothing.
     Tom controls R1 and R2 and can repeat them; he needs one edit by Ines in a gap.
  2. *A copy.* "Copy to my snippets", Duplicate, and every move between profiles (§3.3: "a copy
     made by the device") create a row; C17 makes its creator the author. A held snippet copied
     into the reader's own folder is not held there, on any of their devices.
  3. *A re-push.* After a restore, whichever device re-pushes a row first is the caller of a
     write that differs from the restored row (C18). If that is the reader's device, the
     member's unreviewed content is the reader's.
- Fix: (1) the server also compares the six fields with the *base* version (it has it in the
  history, as C3 needs): when they are equal, the write did not change the content and takes
  the base's `content_by` and `content_at`. A client cannot use this to pass its own content
  off as someone else's, because the comparison is the server's. (2) The store refuses to copy
  a held snippet until it is reviewed, or copies the approved content. (3) A re-push that
  differs from the restored row sets `content_by` to nobody; D10 treats "nobody" as someone
  else, and the devices that wrote or approved that content already hold it as approved.
  Scenarios to add for (1) and (2).

### 6. With three writers the first loser is out of reach — medium, by reading

- Rules: C3, "a newer conflict on the same row closes the older one as `replaced`"; §5.6, "at
  most one conflict per row is open"; §5.12 keeps a version only "while an open conflict names
  it" and deletes a closed conflict after 30 days.
- Sequence: `s1` at R0 in a folder three people may change (or on three devices). All three
  edit offline. Tom's push: R1. Ines's push, base R0: R2, conflict 1 (winner Ines, loser R1).
  Jun's push, base R0: R3, conflict 2 (winner Jun, loser R2), and conflict 1 becomes
  `replaced`. Tom's version is in the history, its conflict was closed by no one, Tom is not a
  party to conflict 2, and Jun is not offered R1.
- With two writers this does not happen: the loser of the first conflict is then an ancestor
  of the winner of the second.
- Fix: conflict 2 takes over the losers of the conflict it replaces (a conflict has a list of
  other versions and of parties), or each unseen version keeps its own open conflict.

### 7. Restore — medium, by reading; the kind of backup checked in the documentation

- *C13 against C18.* A row created after the backup is unknown to the restored server. Its
  re-push is a `put` with a base above 0 for an unknown id: `rejected: gone` under C13, and
  the device moves it to the kept list and removes it (D5). S43 answers `s2` `applied`. C18
  speaks only of "a row nobody has written in the new epoch". One sentence in C13 settles it;
  left as it is, a server built from C13 removes every row created since the backup from every
  device.
- *`repush` is not bounded.* Once C13 excepts re-pushes, a changed client can bring back any
  purged row by setting the flag. Accept it only for a revision between the base of the lost
  epoch's successor and that epoch's first revision.
- *The threshold.* `base_rev` is "the value of `rev_seq` when the epoch began, that is, the
  last revision the restored backup knew" (§5.11). These are not the same. A sequence is not
  part of a transaction: a push that drew revision N before the point of the restore and
  committed after it is lost, and N is at or below the restored counter. A device that pulled
  N does not re-push it ("above `repush_above`"), and under D3 it never takes the server's
  older row. With a logical dump the gap is wider, since a sequence's value is not part of the
  snapshot the rows are read from (by knowledge of Postgres, not tried). Supabase's daily
  backups are physical on current versions (checked), so the window is a moment; it is not
  zero.
- *Rows only the server writes.* Memberships, profiles and invitations are not re-pushed
  (§7.1, C16). A member removed after the backup is a member again and their devices receive
  the folders again. The owner's device holds the membership's tombstone in a revision of the
  old epoch; the restored row has a lower one, D3 calls it `stale`, and the owner goes on
  seeing the person as removed. An account deleted after the backup exists again. I3 forbids
  the repair.
- *A late `begin_epoch`.* "A forgotten step heals at the first device that notices": until
  then devices that were behind the backup write under the old epoch with revisions the lost
  timeline already used, and the base is taken when the function finally runs, above the true
  point.
- Fix: in the resync that follows an epoch change, compare row by row instead of by one
  threshold: a synced row the server lacks, or holds in an older revision of the old epoch, is
  re-pushed; a server-only row is taken as the server has it, whatever its revision. Add to
  the restore procedure that the interface stays closed until `begin_epoch` has run, and that
  account calls made after the backup are lost: owners and admins are told to look at their
  members. Scenarios to add: a membership removed after the backup; a row only one device
  holds.

### 8. Two installations with one device id — medium, by reading

- Rules: the device id is in `sync_state` (§3.2); `hello` refuses an id "that belongs to
  another account" (§6.2) and otherwise "creates or updates the device row for the token's
  session"; C3 records a conflict only when "the version it replaces was written by another
  device".
- Sequence: the data directory is copied to a second computer (the system's migration tool, a
  restored backup of the home folder), and both are used. Each signs in, or carries the
  tokens over. They push under one id: a stale write of one over the other's edit is "the
  same device's own earlier write" and records nothing. They share the receipts of C15, and
  each `hello` moves the row to its own session, so the other is answered `device_unknown` and
  calls `hello` again. A directory restored on the same computer does the same against its
  own later writes.
- Fix: keep a random installation secret outside the data directory (the keychain, which
  ADR-0020 already uses) and send its hash with `hello`; a mismatch for a known id makes the
  device take a new id and resync. Or let the server keep, per device, the highest position
  it served, and treat a `hello` that reports a lower one as a copy. Scenario to add.

### 9. "Or they wrote it last" — medium, by reading

- Rules: §5.13: a tag is readable when "… or they wrote it last"; `attachment` "as `tag`";
  `attachment_blob` "is verified and they can read an attachment row with its profile and
  hash"; the stored file follows the blob. §4.3: an attachment row may be created with "`edit`
  on at least one folder of the profile". C19: "several rows may name the same profile and
  hash". §6.11: the push result says `blob: missing` or not.
- Sequence, in the state of S28 but with the share "to change": Tom pushes an attachment row
  in Ines's profile with the SHA-256 of a file he thinks she has (`at2`, the card). The result
  is not `missing`: she has it. Tom wrote his row last, so he reads it; the blob with that
  profile and hash is verified and he reads a row with them; the file `P/<hash>` is his to
  download. §4.5 says a request for any other file "answers as for a file that does not
  exist", and S28 says so of `at2`. He must know the hash, which usually means he has the
  file; a hash from a list is enough to learn that she has it.
- After Tom is removed, or the share ends, his rows are still "written last" by him: the tags
  he created and every attachment row he made stay readable, with their files, until the
  purge (30 plus 30 days). G13 ("the former reader's next query returns no row of that
  content") and the last-but-one line of §4.5 fail.
- Fix: "wrote it last *and* may still change a folder of that profile"; a blob and its file
  are readable only where a live link from a readable snippet names an attachment with that
  hash, and for the uploader while their `pending` row is open; `begin` answers `exists` and
  the push answers `blob` only from what the caller may read, and otherwise lets the upload
  happen and verifies it.

### 10. A revoked device registers again — medium, by reading; the token's life checked

- Rules: §5.3, "a call is refused unless the token's session belongs to a device row that is
  not revoked"; §6.2 as quoted in finding 8; §11.3, "access stops at once and not when a token
  expires". Supabase's access tokens are checked by signature until they expire; ending the
  session stops the refresh, not the token (sessions guide).
- Sequence: the owner revokes device D. Whoever holds D, or its token, calls `hello` with a
  new device id and the same token. The text lets `hello` create a row for that session; from
  then on the session "belongs to a device row that is not revoked", for the rest of the
  hour.
- Fix: at most one device row per session; a revoked row is kept at least as long as a token
  of its session can live; `hello` refuses a session with a revoked row (`device_revoked`);
  and the device check also requires that the session's row still exists in the
  authentication service. Whether a database function may end a session there is unconfirmed
  (§6).

### 11. Folders left behind after a resync — medium, by reading

- Rule: D7, "Rows with unsent changes, and the folders above them, are left alone; the push
  that follows settles them (C13, D5)." D5 settles the row. Nothing settles the folder.
- Sequence: S23 as written. `f2` and `s4` were purged on the server; B has an unsent edit of
  `s4`. The resync leaves `s4` and `f2`. The push of `s4` is `rejected: gone`; D5 keeps the
  change and removes `s4`. `f2` is a synced row of B's own profile that the server does not
  know, with no entry; the access check looks at other profiles only. S23's note says "and
  then f2" and cites no rule; its outcome (`f2` absent on B) does not follow.
- Fix: `ReconcileEnd` returns what it left alone; after the push the agent calls it again for
  those rows.

### 12. The owner deletes a shared folder — medium, by reading

- Rules: §5.4, "a folder keeps its entries while it is a tombstone, so that its delete can be
  read"; C21, "a deleted folder is not revoked: it is delivered as a tombstone"; C6, the
  delete also deletes "every live share of those folders (C21 then ends the access they
  gave)"; §5.4's invariant derives the entries from the shares.
- Either the members' entries survive the share for 30 days (then §4.2 needs a clause, and
  C7 must say what a member with a surviving `edit` entry may restore), or they go with it.
  In the second case the members' feeds get a `row` entry for each cascaded row, each
  delivered as null. D3 removes a null row; the store's `snippet.folder_id` has no cascade
  (`0001_initial.sql`), so a folder whose snippets come in a later page, or are held back by
  D2 because of an unsent change, cannot be removed: "the store refuses a row of a page",
  three times, then a resync, whose access check purges the folder and keeps the changes.
  It converges, by the longest road, and no scenario shows it.
- Fix: treat the end of a share by the folder's delete like any other end of a share:
  `folder_revoked` for the root to those who read it through the share, tombstones only to
  those who read it through ownership or membership. Scenario to add, with an unsent change
  on the member's device.

### 13. Rows of another profile that outlive their link — medium, by reading

- Rule: D6's clean-up ("rows of other people's profiles that nothing the device still holds
  uses", with the cached files) runs in `PurgeFolder`. D3 has none.
- Sequence: Ines takes the tag "money" off the one shared snippet that carried it, or removes
  an image from it. Tom's device gets the link's tombstone. The tag row, or the attachment
  row and its file, is no longer readable on the server (§5.13) and no entry says so, because
  the tag itself was not written. Tom's device keeps the name, or the file.
- Fix: after a page that tombstones or removes a link or a snippet of another profile, the
  store runs the clean-up of D6 for that profile. I1 then holds for these rows.

### 14. The invariants as an oracle — medium, by reading

Local changes that end in none of the six places of §1, each by a rule of the design:

| Change | Rule | Where it ends |
| --- | --- | --- |
| A save replaced by a later save on the same device before it was sent | D1, S27 ("existed only on A") | Nowhere; intended |
| A move the server did not make | C8, S13 | Told (`adjusted`), not kept |
| A change to a share that was stale | C11, D5, S37 | Told (`superseded`), not kept |
| A refused delete | D5 ("for a `put` …") | The row comes back; not listed |
| An attachment row that differs from the stored one | C19 | `unchanged` |
| A local row equal to one of the account, or a folder merged by name | D9 | Dropped |
| Unsent changes to shared folders at sign-out | D14 | Dropped after a question |

I1 says a device "holds exactly the rows the server shows that user, in the same revisions".
The server shows tombstones for 30 days; a device ignores a tombstone for a row it never had
(D3) and purges by its own clock (D8). The scenarios already compare `deleted` with `absent`.
I1 needs "live rows", and the exception for finding 13 until it is fixed. I6 holds only between
devices that have synced.

Fix: add the places to §1 as the simulation must count them, so that 4.4 does not write its
own definition of a lost edit.

### 15. The check accepts contradictory outcomes — medium, demonstrated

Each line is one change to a copy of `spec/sync/scenarios.toml`;
`every_scenario_has_a_defined_outcome` passed on all eight.

| Scenario | Change | What it would mean |
| --- | --- | --- |
| S01 | `start` taken out of the history of `s1` | A replaced version the server did not keep |
| S03 | The conflict's kind `delete_over_edit` → `edit_over_delete` | A kind that contradicts the deleted row |
| S31 | Server row `s1` at version `c1`, the answer still `rejected:forbidden` | A refused write that was applied |
| S30 | `kept = ["c1", "c2"]` removed | Refused changes kept nowhere: a lost edit |
| S01 | Device B's `s1` set to version `a1`, the server's `b1` | Two online devices of one account that differ |
| S22 | `s3` at version `b1`, a step that edited `s1` | A version from a step that never wrote the row |
| S01 | `shown = []` on both devices, the conflict open | A conflict shown to nobody |
| S16 | `conflicts = []` | An unseen row deleted with its folder, no conflict: a lost edit |

The check is structural, and for the KPI "every scenario has a defined outcome" that is what
is asked. But §12 and `docs/test-strategy.md` say it fails when "conflicts, history and rows"
disagree, and nothing else looks at the outcomes until task 4.4 exists; findings 11, 22 and 23
are outcomes that do not follow from the rules and passed. Cross-checks that need no model of
the server: a `rejected` answer to a `put` of a device's step puts that step in the device's
`kept` (shares excepted); a `blocked` answer puts it in `blocked` and leaves the outbox above
0; `applied+conflict` on a step means a conflict with that step as winner; an open conflict's
kind fits the row's state; the parties' devices show `conflict`; a row's version is a step
that names the row, or a step declared to cascade to it; every version a step wrote that is
not current is in the history unless its answer was not `applied`; devices of one account that
end online hold the same rows unless one has a blocked change.

### 16. Read functions that must write, and policies that need helpers — medium, by reading

- §5.1 makes `pull`, `fetch_folder` and `snapshot` `security invoker` "so what they return
  passes through the policies". The same functions must: count the call in `rate_bucket`
  (§6.8), which §5.13 lets nobody read and no grant lets anyone write; compare the device's
  protocol with `server_state` (C23) and its epoch (§6.4), which nobody may read; refuse a
  revoked device and keep `last_seen_at`, which decides the 180-day removal; and, in `pull`,
  run `begin_epoch` (C18). Each needs a definer helper that the caller's role can execute.
- The policy for `membership` ("it is live and they have a live membership in the same
  group") reads the table it protects, and "every rule also requires that the token's session
  belongs to a device that is not revoked" does the same on `device`. Postgres refuses such a
  policy with a recursion error; the documented way is a definer function in a schema the
  REST interface does not expose, which the role must still be able to execute.
- So "`iamb_private` holds helper functions that no client can call" and G4 ("no role a
  device can have may … call anything in `iamb_private`") cannot both hold with §5.13 and
  §6.8. Row-level security "forced" on every table is harmless only because the functions'
  owner bypasses it on Supabase (checked); say so, or 4.3 will read it as a guarantee.
- Fix: list the helpers by name with what each returns; say that reads go through one invoker
  query for the rows and definer helpers for the rest; reword G4.

### 17. A push that can never succeed — medium, by reading; the time-out checked

- Rules: §6.1, "a function that fails unexpectedly rolls its transaction back and is retried
  the same way"; §6.8, "a push that fails blocks later pushes"; §6.3, a cascade list of up to
  20,000 rows counts as one op. Pulls have a bound ("after three tries the agent resyncs");
  pushes have none.
- The role devices use has a statement time-out of 8 seconds by default on Supabase, 60
  seconds at most through the REST interface. Deleting a folder of some thousand snippets
  writes, per row, a revision, a history row and a feed entry per reader, plus the access
  entries. A request that exceeds the time-out fails the same way every time. So does any op
  that hits a defect in the function.
- Fix: after n identical failures the agent sends the changes of the request one at a time; a
  change that fails alone m times is marked blocked with the reason `server_error`, with what
  depends on it, and shown as such. Bound a cascade to what the time-out allows and let the
  server finish larger ones in parts. Name the time-out of each function in §5.14.

### 18. The shared root when it is a sub-folder — medium, by reading

- §4.3: "Sub-folder · Change: name, defaults, position, moving within the access root: `edit`
  on it and on the new parent." A folder shared from inside the owner's tree is a sub-folder,
  and the share gives `edit` on it. A top-level shared folder needs `manage`.
- Against: §4.2 ("sub-folders inside"), ADR-0014 ("never the folder itself"), architecture
  §7's table ("its owner only"), and the sentence of flow 6, step 3.
- Fix: one more row in §4.3 for "the root of a share", `manage` for every change.

### 19. `{snippet}` is not held — medium, by reading

- D10 holds `{key}`, `{wait}`, `{clipboard}` and line breaks. A `{snippet}` reference
  resolves in the reader's own library (template specification §4.4: "as if it were written
  in place: its macros run"), private folders included.
- Sequence: Tom changes the shared `;hrs` to `Open 9 to 5. {snippet abbr=";iban"}`. One line,
  not held. When Ines types `;hrs` in a customer's chat, her private snippet is typed too,
  with its own key presses if it has any.
- It is also a wanted use (a shared reply that ends in each member's own signature), so the
  answer is the owner's: hold a change by someone else that adds or changes a reference, or
  keep it open and add it to "what is left" in §11.3.

### 20. Open question 7 — medium

The recommendation "every member" is argued with "a share only adds a folder that members can
leave unused". Under §6.7 and flow 6 the folder is on every member's device within ten
seconds and "the other 17 work now". There is no step at which a recipient accepts a folder
and no way to switch one off. Combined with ADR-0022's free pass for single-line text, any
member of a team can make text expand on every colleague's machine for abbreviations they do
not use yet. For a family that may be right. The question should state it and offer the two
ways out named in the table.

### 21. Adoption can stop half-way — medium, by reading

D9: one transaction adopts; then "the agent resyncs"; "then the store merges"; then "every
remaining row that was never synced is queued". A stop after the first transaction leaves the
library under the account with rows at revision 0 and no outbox entries. No rule queues such
rows later, and D8 treats "revision 0, no account" tombstones only. Keep the phase
(`adopted`, `merged`, `queued`) in `sync_state` and resume at start, or queue everything at
adoption and let the merge delete the entries of what it drops.

The design's §13 now has eleven questions: 1 with the clause of finding 35; 3 with what a

The design's §11.6 takes up the table of §6 line by line. Checked in Supabase's documentation
for this revision: that time-boxed sessions and inactivity time-outs need a paid plan (sessions
guide); that a function's own `statement_timeout` is honoured through the REST interface, up to
60 seconds (timeouts guide); the realtime connection quotas and the error a refused join gets
(realtime quotas); that Supabase Cron runs database functions on a schedule (cron guide; the
page does not say on which plans); the edge function limits (256 MB, 2 seconds of processor
time, 150 or 400 seconds); what the administrators' interface does when a user is deleted, and
that issued tokens outlive it (managing user data guide); and the three sign-out scopes
(sign-out guide). Removed from the design: the trigger on the authentication service's user
table (`hello` creates the profile) and any need for a database function to end a session or
delete an account there. Left as verification steps, each named in §11.6 with the task that
makes it: that a policy's helper pattern works per table, that a function's time-out applies on
the deployed project and a 2,000-row cascade fits, that the restored revision counter is not
below a restored revision, that the functions' owner may read `auth.sessions` and `auth.users`,
that the plan has Cron, how the interface is closed during a restore (all task 4.2); that an
edge function hashes a 25 MiB file within its limits (task 4.6); and that no enabled identity
provider yields a confirmed address it has not verified (task 4.3).
