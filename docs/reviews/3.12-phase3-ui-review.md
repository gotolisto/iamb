*Update after the fixes (§5):* the high finding and the six medium ones are fixed in the

The privacy and sanitising core holds up. I found no path by which a form value, a palette

a file, the web view's storage or a broadcast event: the values travel in `Secret` inside the

The high finding is a stuck state: an open fill-in form can become unreachable, and while it is

fails half way) and a pasted media file whose extension comes from the alt text.

## 3. Details of the high and medium findings

### 1. An open form can become unreachable, and then nothing expands — high, by reading

Code path:

- While a form is open the engine drops every typed match, not only those with fields:
  `engine.rs:565` `if self.form.is_some() { self.buffer.clear(); return diagnostic(… FormOpen …) }`;
  palette picks (`:751`) and `ReopenLastForm` (`:852`) likewise. The UI host's palette refuses to
  open while a form is open (`palette.rs:615`). The service has no timeout for a form session
  that was acknowledged.
- When the panel does not hold the keyboard, the form thread polls the front application
  (`form.rs:1111-1138`). A front window of another process hides the panel (`away = true`); the
  panel comes back only when a window of the token's process is in front again:

  ```rust
  if front.pid() == token.pid() {
      if open.away { … self.take_keyboard(open); }
  } else if !open.away && open.visible {
      self.cfg.host.hide(); open.visible = false; open.away = true;
  }
  ```

  If that process has quit (or crashed) while the panel stepped aside, it never comes back, and
  nothing else ends the form: the connection is up, the user cannot press Esc on a hidden panel,
  the palette will not open, and the tray's reopen is dropped by the engine.
- The panels' close request is handled without the flow: `windows.rs:167-170`
  `CloseRequested { api, .. } => { api.prevent_close(); let _ = handle.hide(); }`. The form
  controller still has `visible = true`. The focus loss that follows makes it send
  `PanelFocus(false)` (so keys reach the app again), but nothing re-shows the panel while the
  token's app is in front; it reappears only if the user switches to another app and back, which
  nobody would guess. On Windows, Alt+F4 on the focused panel is the obvious trigger
  (unconfirmed: a borderless WebView2 window may or may not receive it; check on a Windows
  machine with the form open).
- The "could not get back" banner (flow 4) tells the user to "Click where the text should go and
  press Insert again", but the hand-back always goes to the original token (`form.rs:925-934`).
  When that window is gone, clicking into another app makes the panel step aside (the path
  above), and clicking into another window of the same app leads to the same failure on every
  Insert. Cancel then also drops the answers, because only a refused submit keeps them.

Failure scenario: a user types `;rlate` in a mail window, the form appears, they switch to the
browser to look something up (the panel steps aside), and the mail app is closed meanwhile or
crashes. From then on no abbreviation expands anywhere, with no visible reason, until Iamb is
quit from the tray and started again (or the service restarts). The log shows `form_open` for
every attempt.

How I know: by reading the three sites above and the engine's form handling; there is no test
of the step-aside path (`tests/form.rs` covers keyboard loss in place, not an app switch). A
mock-focus test that moves the front window to a second process, then removes the token's
process, and then types a plain abbreviation, would demonstrate it.

Fix: cancel the form (and the palette) when the token's process no longer exists, which the
platform's focus inspector or a process check can tell; handle `CloseRequested` on the form as
Cancel and on the palette as Esc; give a stepped-aside form a way back (the tray's "Fill in the
last form again…" or the palette shortcut could bring an open form to the front instead of being
dropped); consider whether typed abbreviations without fields should really be dropped while a
form waits in another app.

### 2. "Try the form" is never offered — medium, demonstrated by reading

`TemplatePreview` draws the button only when it gets `onTryForm` (`TemplatePreview.tsx:126`).
`TemplateField` forwards `props.onTryForm` (`TemplateField.tsx:986`) and `props.previewValues`,
but the editor's only `TemplateField` (`Editor.tsx:647-657`) passes neither, and no other code
renders a preview. The spec lists the button in §4.3 ("'Try the form' opens the real fill-in form
and feeds the preview"), flow 2 step 5 draws it, and flow 4 lists it as an entry point. Nothing
in the README or the test strategy records it as deferred.

### 3. No notice when a pick or an insert is refused — medium, by reading

Owner decision 4 (spec §12) keeps notices for exactly this case, §4.11 gives the copy, and the
error tables of flows 4 and 5 list the sentences per reason. Spec §11.2 entry 8 says the service
has no outcome event yet and gives the interim rule: "The UI matches a `DiagnosticAdded` for the
same snippet within 3 s of its request". Nothing implements it: the `refused_*` sentences exist
only in `src/library/diagnostics/reasons.ts`, used by the log view. After a palette pick or a
form Insert the panel hides, and if the engine refuses (password field, excluded app, composing,
injection busy, the snippet deleted) nothing is typed and nothing is said. For a refused form the
answers are kept for 30 minutes, but the user is not told to press the shortcut where the text
should go. The palette's own `pickFailed` sentence covers only a failed command, not a refusal,
which arrives as a successful `ExpandSnippet` followed by a diagnostic.

### 4. The tray's palette and reopen target Iamb's own window on Windows — medium, unconfirmed

`open_from_tray` reads the front window when the menu item's event is handled
(`palette.rs:546-552`), and a token of the UI host's own process makes the palette a "library"
palette (`palette.rs:631`). On Windows the tray crate brings its own hidden window to the
foreground before `TrackPopupMenu` (`tray-icon` 0.25.1, `platform_impl/windows/mod.rs:551-567`,
"bring the hidden window to the foreground so the pop up menu would automatically hide"), so when
the item fires the front window is Iamb's. The palette then selects picks in the library instead
of typing them, and the show may not get the keyboard (the service granted no foreground right).
"Fill in the last form again…" sends `ReopenLastForm`, which "runs against the window that has
the focus when it arrives" (`tray.rs:146-148`): Iamb's own, so it is refused. On macOS the menu
bar does not change the front application, so both work there. The test
`the_tray_opens_it_for_the_app_in_front_and_a_pick_types_there` passes because the mock does not
model the menu taking the foreground.

Confirm on Windows: focus Notepad, open the tray menu, choose "Search snippets…", pick a snippet.
Expected by flow 5: it is typed into Notepad.

### 5. A page reload in WebView2 drops unsaved edits — medium, unconfirmed

WebView2 keeps its browser accelerator keys by default (F5, Ctrl+R, Ctrl+Shift+R reload; Ctrl+P,
Ctrl+F); the window builders (`windows.rs:120-139`, `:340-348`, `onboarding_commands.rs:129`) do
not turn them off, and the front end has no `beforeunload` handler. In the library window a
reload discards the editor's draft without the "Not saved" guard of spec §4.3 (the window-close
guard in `LibraryView.tsx` covers only the close request). In the form panel a reload loses the
answers typed so far (the panel refetches the form, so it recovers otherwise). Confirm on
Windows: edit a snippet, press F5.

### 6. A multi-delete that fails part way loses Undo — medium, by reading

`deleteSnippets` (`Library.tsx:455-470`) fetches every row for Undo, then runs
`await Promise.all(full.map((s) => api.deleteSnippet(s.id)))`. If one delete fails (the service
restarting, a timeout, a row removed elsewhere between the read and the delete), `Promise.all`
rejects while the other deletes still complete; the catch shows the error toast and returns, and
`full`, the only copy of the deleted rows, is dropped. Spec §4.2 replaces a confirmation with the
10-second Undo, so these deletes are now permanent. No test covers a failing delete in a
selection.

### 7. The offered media file takes its extension from the alt text — medium, by reading

When a formatted snippet is nothing but one media attachment, the service also offers it as a
file (ADR-0018). `resolve_content` names the copy from the image's alt text
(`rich.rs:144`, `clean_file_name(&unescape_html(tag.alt), fallback)`), which removes path
separators and control characters but keeps any extension, and `offer_file` writes it under
`run/paste/<sha256>/<name>` (`rich.rs:188-197`). The type check that admitted the bytes is a
prefix check (`attachments.rs:92`: `%PDF-` makes a PDF). So `![Invoice.cmd](attachment:<sha>)`
with bytes `%PDF-1.7` followed by command lines pastes a file `Invoice.cmd` into a mail or a
folder; `cmd.exe` reports an error for the first line and runs the rest. `.hta` works the same way
with HTML after the prefix. Such a library arrives today through Import (the JSON format carries
attachments and the import checks only type, size and hash) and in Phase 4 through shared
folders, where the review rule of §8 rule 10 does not look at attachments. Fix: name the file
`<cleaned stem>.<extension of the sniffed type>`.
