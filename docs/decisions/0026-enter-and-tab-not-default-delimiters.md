# ADR-0026: Enter and Tab are not default delimiters

Status: accepted (the owner chose this after the Phase 2 privacy review)

**Context.** Architecture §4.4 made Enter and Tab default delimiters, and ADR-0010 says the listener never holds a key back. Both cannot hold safely for keys the application acts on. The application receives the real Enter or Tab first: Tab moves to the next field of a form, Enter sends a message or closes a dialog. Iamb's deletion, expansion and second key press arrive after that, in whatever has the focus by then. The service cancels only if the focus notification reaches it before the injector's start marker comes back, which takes well under a millisecond. The privacy review (task 2.8, finding 1) showed on the mock that the expansion lands in the password field in nearly every round once the notification is 0.1 ms late, deleting characters of that field first.

**Decision.**
1. The default delimiter set is space and `. , ; : ! ? ) ] } " '`. Enter and Tab end a word (they clear the buffer) without expanding it.
2. A user can add Enter (`\n`) and Tab (`\t`) to the `delimiters` setting. The settings screen (Phase 3) must say what that does in forms, chats and dialogs when they are turned on.
3. Independently, both injectors check the focus themselves (architecture §4.6). The request names the window the trigger was typed in; right before the start marker the injector refuses to start when the keys would go to another window (on macOS, another application), and from there it stops between steps when the window, process or field it can see changes. So a trigger that loses the race to another window taking the focus is caught at the start check or between steps, whether the move came before the start marker or after it (the follow-up review's N1: its probe, 300 rounds per case on the mock, went from 286 to 300 expansions typed into the password window with the focus report 0.1 to 5 ms late, and 4 to 5 with it immediate, to 0 in every case). A check and the send that follows it are still two moments: a move that lands between them lets that one step through. The close-out review (C4) measured this on the mock at about 0.7% of rounds with the move aimed into that gap, against 26% before the start check; no check can close it, because the system offers no way to send keys only if the focus is still where it was. What stays open is a move to another field of the same window before the start marker, which the injector cannot tell from staying put: on Windows a browser engine's fields share one window, and on macOS only the frontmost application is compared. That is the case Enter and Tab cause in a form, and the reason for item 1; a user who adds them accepts it (item 2). After the start marker a field change is still seen where the guard can see fields (the focused control on Windows, the focus notifications on macOS), and steps sent before it stay where they went.

**Consequences.** Abbreviations at the end of a line or a form field need a space or punctuation, or an immediate trigger. So that this is not a mystery, an Enter or Tab after an abbreviation that would have expanded after a delimiter records the diagnostic `not_a_delimiter`, naming the snippet (Phase 3). Sessions that test Enter and Tab as delimiters now set them explicitly. The compatibility matrix is unaffected: it uses immediate triggers.

**Rejected.** Keeping them and waiting a fixed time after the key for a focus notification: it adds delay to every such expansion and still loses to a slow application or browser accessibility layer. Keeping only Enter: Enter still sends chats and closes dialogs before the expansion arrives.
