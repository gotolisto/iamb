# ADR-0031: A conflict offers what its reader could read; a request locks what its caller has a part in

Status: proposed (the follow-up to the security review of task 4.3, `docs/reviews/4.3-security-review.md`; awaiting the owner's approval). Amends ADR-0027, whose rules it otherwise keeps.

**Context.** ADR-0027 records a conflict when a write replaces a version its device had not seen, and lets a newer conflict on a row take over every version the older one offered, "with their authors as parties" (C3). It lets "any party" close a conflict and lets a party restore a version with "the right to write the row now" (C20). The security review carried out three attacks that follow those words and break what the same design promises elsewhere: a member with `edit` on one shared folder read a version that was written while the snippet was in the owner's private folder, and one from before the folder was shared (§4.4 and §4.5 say: nothing of the owner's but the shared tree, and no history); a removed member went on being told of conflicts in the folder he had left and closed one for everybody (§11.3 and G13 say: nothing new from the moment the removal commits); and a member put a folder of the group at its top level by restoring a version, which a push of the same row refuses (§4.3). Two further findings come from the rule "one writer per profile at a time" (C24): a row id is unique across all profiles, so two requests that name one new id in two profiles held different locks, and the second became an unchecked update of the first one's row; and a request locked every profile it named before it looked at any right, so whoever knew a profile's id could stall its owner's writes.

**Decision.**
1. **Parties stay what they were; taking part needs access.** The parties of a conflict are still the winner's author and the author of every version it offers, and a newer conflict still takes over the versions of the open one, so that no version replaced unseen drops out of reach of the people it belongs to. But a party takes part in a conflict only while they can read its row: only then is it listed for them, announced in their feed, readable and theirs to close. For a party who cannot read the row the conflict is not there (`not_found`), from the transaction that ended their access.
2. **A version is offered to a party who wrote it or could read it while it was the row.** The server keeps, with each access entry, the value of its revision counter when the entry began (`folder_access.since_rev`); a version replaced by a revision above that number, in a folder the entry is for, was the row while the entry existed. A version from a folder the party could not read, or replaced before the party's access to its folder began, is not listed and cannot be restored by that party, however it came into the conflict. The same rule decides whether the base version of a write may be used to name an author (C17) or to judge a change (C3): a base the writer could not read "cannot be found". Revisions decide, not clocks: every write of a profile and every change of access to it are serial under the profile's lock.
3. **"Restore this version" is a push.** The server builds the op a device would send for that version, based on the row's current revision, and runs it through the code that judges every pushed op; only the author of the content is carried over from the version. Whatever §4.3, C7 and C8 say about a push of that row by that user holds for the restore, by construction.
4. **A request locks only what its caller has a part in, and a new id is locked across profiles.** Before any lock, an op whose profile the caller has no grant in is answered as for a profile that does not exist; account calls check the membership before they lock and again under the lock. After its profile locks a push locks the id of every row its ops name and reads the rows again: a create inserts or fails, and an update names the profile it expects. An answer about something the caller cannot see is the answer for something that does not exist, wherever that is possible (a delete, a profile, a group); it is not possible for a create with an id that is in use, which must be refused.

**Consequences.** S57 (three people who shared the folder throughout) is unchanged. A member can see less in a conflict than its other parties, and the conflict view must not assume that every party sees the same versions: the server sends each reader the versions on offer to them and no word about the others. A removed member who is invited back sees the conflicts on rows they can read again, with the versions written since they came back and those they wrote themselves. A restore can now be refused (`forbidden`) where it was applied before, and answers `invalid` for a version that is not on offer to the caller. `get_conflict` no longer answers `forbidden`. A delete of a row the caller cannot read is answered `unchanged`, and an op on a profile or group the caller has no grant in `rejected: parent_gone`, where both were `rejected: forbidden`. `folder_access` has one more column, which the device never sees. Three scenarios state the outcomes (S85, S86, S87), and the server's tests hold each attack as a test that failed before.

**Rejected.** *Dropping a user from `parties` when their access ends*: simpler to read, but the scenario check requires a conflict's parties to be the authors of its versions, the version a removed member wrote must stay on offer to the others, and a member who is invited back should find the conflict on their own edit again; the access check at every use gives the same protection and needs no bookkeeping. *Handing a taken-over version only to the parties of the conflict it came from*: it would withhold a version from somebody who read it at the time (S57's third writer). *Comparing times (`granted_at` against the time a version was replaced)*: `granted_at` is the time access to the root began and is inherited by folders that come into the tree later, and two writes of one request can fall into one millisecond. *Keeping a separate check for restores*: that is how the restore came to allow what a push refused.
