# ADR-0031: A conflict offers what its reader could read; a request locks what its caller has a part in

Status: proposed (the follow-up to the security review of task 4.3, `docs/reviews/4.3-security-review.md`; revised after the re-verification of the fixes, `docs/reviews/4.3-security-reverify.md`; awaiting the owner's approval. Point 6 is the owner's decision on that re-verification's N5, taken on 2026-11-27). Amends ADR-0027, whose rules it otherwise keeps.

**Context.** ADR-0027 records a conflict when a write replaces a version its device had not seen, and lets a newer conflict on a row take over every version the older one offered, "with their authors as parties" (C3). It lets "any party" close a conflict and lets a party restore a version with "the right to write the row now" (C20). The security review carried out three attacks that follow those words and break what the same design promises elsewhere: a member with `edit` on one shared folder read a version that was written while the snippet was in the owner's private folder, and one from before the folder was shared (§4.4 and §4.5 say: nothing of the owner's but the shared tree, and no history); a removed member went on being told of conflicts in the folder he had left and closed one for everybody (§11.3 and G13 say: nothing new from the moment the removal commits); and a member put a folder of the group at its top level by restoring a version, which a push of the same row refuses (§4.3). Two further findings come from the rule "one writer per profile at a time" (C24): a row id is unique across all profiles, so two requests that name one new id in two profiles held different locks, and the second became an unchecked update of the first one's row; and a request locked every profile it named before it looked at any right, so whoever knew a profile's id could stall its owner's writes.

**Decision.**
1. **Parties stay what they were; taking part needs access.** The parties of a conflict are still the winner's author and the author of every version it offers, and a newer conflict still takes over the versions of the open one, so that no version replaced unseen drops out of reach of the people it belongs to. But a party takes part in a conflict only while they can read its row: only then is it listed for them, announced in their feed, readable and theirs to close. For a party who cannot read the row the conflict is not there (`not_found`), from the transaction that ended their access.
2. **A version is offered to a party who wrote it or could read it while it was the row.** The server keeps, with each access entry, the value of its revision counter when the entry began (`folder_access.since_rev`); a version replaced by a revision above that number, in a folder the entry is for, was the row while the entry existed. A version from a folder the party could not read, or replaced before the party's access to its folder began, is not listed and cannot be restored by that party, however it came into the conflict. The same rule decides whether the base version of a write may be used to name an author (C17) or to judge a change (C3): a base the writer could not read "cannot be found". Revisions decide, not clocks: every write of a profile and every change of access to it are serial under the profile's lock. **"While it was the row" means in a state of the server the party could have seen.** An entry's number is taken when the request that made it has ended, at or above every revision that request drew, because a push applies its ops in dependency order and not in the order the device made them: a version replaced in the push that shared its folder was never visible to the member, whichever op the server applied first (the re-verification's N1). For the same reason a version that one request wrote and replaced is offered to its writer alone.
3. **"Restore this version" is a push.** The server builds the op a device would send for that version, based on the row's current revision, and runs it through the code that judges every pushed op; only the author of the content is carried over from the version. Whatever §4.3, C7 and C8 say about a push of that row by that user holds for the restore, by construction.
4. **A request locks only what its caller can write in, and a new id is locked across profiles.** Before any lock, an op whose profile the caller has no grant in is answered as for a profile that does not exist, and an op in a profile the caller can only read is judged without the lock, by the same rules, unable to write; account calls check the membership before they lock and again under the lock. After its profile locks a push locks the id of every row its ops may write (under a 64-bit key made with a seed only the server holds, so that no id can be chosen to share another row's lock) and reads the rows again: a create inserts or fails, and an update names the profile it expects. An answer about something the caller cannot see is the answer for something that does not exist, wherever that is possible (a delete, a profile, a group); it is not possible for a create with an id that is in use, which must be refused.

5. **An answer closes a conflict for those who are offered no more than the party who gives it.** "Keep" or a restore by a party who is offered every version the conflict holds closes it for everybody, as before. By a party who is offered fewer, it closes the conflict for that party alone; it stays open, with every version, for the others (the re-verification's N6: a member answered away the owner's conflict about a private version he could not see).

6. **A tombstone is read by who deleted the row and by those who could read it before it was deleted.** A deleted row stays on the server for 30 days with the content it had, and every read handed it to whoever could read its folder at that moment, also to somebody the folder was shared with after the delete, or who joined the group after it (the re-verification's N5). Point 2 already says what a reader gets of the past: what they wrote or could read while it was the row. The same number decides for a tombstone: through an access entry it is readable only when the reader deleted the row or its revision, which is the revision of its delete, is above the entry's `since_rev`; a deleted tag or attachment row of a group, only for a member whose membership began before the delete. To everybody else the row is not there, for reads and for writes: the feed's entry is delivered as null, a snapshot leaves it out, a `put` on it is `rejected: gone` like one on a purged row, and a `put` below a deleted folder they may not read is `rejected: parent_gone`. A deleted version in a conflict (the tombstone a restore replaced) is offered under the same rule. Three things follow from rows that are not simply "in a folder". The two-device simulation found the first two when the rule was tried without them, against the model of the server; the third follows from the second:
   - *Who deleted a row reads its tombstone.* A device that creates a folder and, offline, deletes a folder above it sends both in one push; the new folder is created and deleted in one request, so no access entry for it is older than its delete, its owner's included. Without the tombstone in the answer the device kept the folder live.
   - *A snippet that changes its folder leaves its deleted links behind.* A link is read through the entry for its snippet's folder, and the snippet can move: its owner makes a new folder and moves it there, and the entry for the new folder is younger than every link that was ever taken off the snippet; or it moves into a shared folder whose readers could not read it when the link was deleted. The server removes a snippet's deleted links when the snippet moves, as the purge would later, so that what it holds of them was deleted where the snippet is now.
   - *A link gives a tag or an attachment row only while that row is live.* A deleted tag that a shared snippet still has a link to (links are not deleted with a tag, C10) was handed, with its name, to every reader of the snippet. Such a reader now gets the delete as a null row, and the links again when the tag comes back.

   **No rule was added on the device.** A device never holds a live copy of a row whose tombstone it cannot get: a reader for whom a tombstone is withheld never had the row, or had it under an access that ended; an access never ends without `folder_revoked` or a null folder, which purge the tree, and never begins without `folder_visible`, whose fetch removes what the device holds of the tree and the server did not send; a device that missed both resyncs. And the server never withholds a tombstone that a device holds under an access that still stands: whether a tombstone is readable depends on its revision, on who deleted it and on the entry, which do not change while the entry stands. The device's list of the calls by which its user took access away (D7) is not involved: this narrows what the server sends and takes nothing away that a device must remember.

**Consequences.** S57 (three people who shared the folder throughout) is unchanged. A member can see less in a conflict than its other parties, and the conflict view must not assume that every party sees the same versions: the server sends each reader the versions on offer to them and no word about the others. A removed member who is invited back sees the conflicts on rows they can read again, with the versions written since they came back and those they wrote themselves. A restore can now be refused (`forbidden`) where it was applied before, and answers `invalid` for a version that is not on offer to the caller. `get_conflict` no longer answers `forbidden`. A delete of a row the caller cannot read is answered `unchanged`, and an op on a profile or group the caller has no grant in `rejected: parent_gone`, where both were `rejected: forbidden`. `folder_access` has one more column, which the device never sees. Eight scenarios state the outcomes (S85 to S92; S88 and S89 have the replacement and the sharing in one push, S90 and S91 a delete before the access began and between two accesses, S92 a tag deleted while a shared snippet carries it), and the server's tests hold each attack as a test that failed before. With point 6 a member's stale edit of a row that was deleted while they could not read it no longer restores the row: it is refused and kept on the device that made it, where before it brought the row back for everybody. A conflict's `state` is now a fact about the reader: closed for one party, it can be open for another.

**Rejected.** *Dropping a user from `parties` when their access ends*: simpler to read, but the scenario check requires a conflict's parties to be the authors of its versions, the version a removed member wrote must stay on offer to the others, and a member who is invited back should find the conflict on their own edit again; the access check at every use gives the same protection and needs no bookkeeping. *Handing a taken-over version only to the parties of the conflict it came from*: it would withhold a version from somebody who read it at the time (S57's third writer). *Comparing times (`granted_at` against the time a version was replaced)*: `granted_at` is the time access to the root began and is inherited by folders that come into the tree later, and two writes of one request can fall into one millisecond. *Keeping a separate check for restores*: that is how the restore came to allow what a push refused. *Taking an entry's number when the op that makes it is applied*: the first form of point 2, which judged "emptied, then shared" in one push as "shared, then emptied". *Closing a conflict for everybody on any party's answer*: it lets a party dispose of versions that party is not allowed to see. *Delivering a tombstone without its content to a reader whose access began after the delete* (option 2 of the review's §12.3): a second wire form, for a row whose device has no use for it, and the row's id and the fact of the delete would still be handed over. *Keeping the behaviour and saying so in the share dialog* (option 3): it asks people to remember what they deleted in the last 30 days before they share a folder. *Reading a link's tombstone through the folder its snippet is in now, whatever the snippet did since*: wrong in both directions once a snippet moves, and it left devices holding tombstones the server no longer showed their user. *Recording, for every reader and snippet, since when they could read it*: exact, and a table the size of readers times snippets. *Letting such a reader's `put` restore the row, as a `put` on any tombstone does*: the row would come back with its live links (C10), and with them tags and files that were never shared with the writer; and a member could bring back, by its id, what the owner deleted while the folder was hers alone. *Counting deleted folders when a folder is moved* (for the fifth level a restored folder could land on): a move would be refused its place because of sub-folders the user deleted and can no longer see; holding the restored folder to four levels touches only the rare restore.
