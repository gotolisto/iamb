# ADR-0028: The data model for sync: no uniqueness on the server, derived share ids, server-written memberships, access entries, authorship of content

Status: proposed (task 4.1; awaiting the owner's approval). Amends ADR-0014 (uniqueness, ids, who writes which row) and ADR-0022 (what an approval is bound to).

**Context.** ADR-0014 makes abbreviations unique among the snippets a user can read, enforced by the store inside a profile and by precedence across profiles; gives every row an id made on the device; and treats all nine entities alike. ADR-0022 holds a snippet "created or changed by another user" and stores the approved revision. Designing sync showed four places where that is not enough. Two devices can each create the same abbreviation offline, and a server that refused the second would leave an edit on one device only. Two devices can share the same folder with the same group, and one can stop sharing while the other, stale, shares again. A membership is what gives access and is subject to the plan, so a device cannot create it. And the user who last wrote a row is not the user who wrote its content: an owner who changes only the label of a snippet whose key presses a member added would make those key presses count as the owner's own on every device.

**Decision.**
1. **The server enforces no uniqueness on content.** It never reads abbreviations, labels, bodies or names except to store them and compare them for equality. The store keeps refusing a duplicate abbreviation in a local edit; rows that arrive by sync are applied as they are, and the unique index on the abbreviation becomes an ordinary one. Which snippet holds an abbreviation is decided on every device by one order: the user's personal profile first; then the other folders by the time the server recorded access to them, then by the id of the shared folder; inside one of these by creation time, then id. The others are listed in library health.
2. **A share's id is derived** from its folder and its group (SHA-256 of a fixed prefix and the two ids, as a UUID of version 8), so a pair has one row everywhere. A change to a share that was made without seeing the row's latest revision is not applied; a delete of a share always is.
3. **Profiles, memberships and invitations are written by the server only**, through account calls that need a connection. Devices receive them through the feed and never queue them.
4. **Access entries.** The server keeps one row per user and readable folder, with the permission and the time access began, in step with shares and memberships inside the same transactions. The read policies look it up, the visibility entries of the feed are its additions and removals, and each device receives its own entries instead of computing permissions.
5. **Authorship of content.** The server sets `updated_by` from the caller, and for a snippet also `content_by` and `content_at`, changed only when a write changes the abbreviation, kind, body, trigger, case mode or word-start flag. A device holds a snippet for review when `content_by` is someone else and the content needs review under ADR-0022, and it stores what it approved as those six fields, not as a revision number; a revision whose six fields equal the approved ones does not ask again.
6. **A row never changes its profile.** Moving content between profiles is a copy and a delete made by the device.

**Consequences.** No edit is refused for a reason the user cannot see at the time they make it; duplicates are visible and each device resolves them the same way. A shared snippet can never take over one of the user's own abbreviations. "Stop sharing" cannot be undone by a device that was offline. Groups and memberships cannot be changed offline. The interface and the server cannot disagree about a permission. The review of ADR-0022 cannot be bypassed by an innocent edit, and a move or a new label by someone else does not ask the user again. The store gains device-local tables (access, origin of content, approved content, kept changes) and loses a unique index; the model's entities are unchanged. Because the server does not interpret content, the content columns could hold ciphertext later (ADR-0029).

**Rejected.** A unique index on the server per profile (cannot cover a user's view across profiles, and turns a duplicate into an edit that never syncs). Renaming a duplicate automatically (changes what the user types without asking). Random ids for shares with a uniqueness check (a re-share after "stop sharing" cannot be told from a stale share). Memberships queued on the device (access granted by a row the server has not checked against the plan and the invitation). Binding an approval to a revision number (asks again after every label change and can be bypassed through the row's last writer). Computing permissions on the device from shares and memberships (two implementations of one rule).
