# ADR-0028: The data model for sync: no uniqueness on the server, derived share ids, server-written memberships, access entries, authorship of content

Status: proposed (task 4.1; awaiting the owner's approval; revised after the independent review of the design, `docs/reviews/4.1-sync-design-review.md`, and again after its follow-up, `docs/reviews/4.1-sync-design-followup.md`). Amends ADR-0014 (uniqueness, ids, who writes which row) and ADR-0022 (what an approval is bound to, and one more thing that is held: open question 10 of `docs/sync-design.md` §13).

**Context.** ADR-0014 makes abbreviations unique among the snippets a user can read, enforced by the store inside a profile and by precedence across profiles; gives every row an id made on the device; and treats all nine entities alike. ADR-0022 holds a snippet "created or changed by another user" and stores the approved revision. Designing sync showed four places where that is not enough. Two devices can each create the same abbreviation offline, and a server that refused the second would leave an edit on one device only. Two devices can share the same folder with the same group, and one can stop sharing while the other, stale, shares again. A membership is what gives access and is subject to the plan, so a device cannot create it. And the user who last wrote a row is not the user who wrote its content: an owner who changes only the label of a snippet whose key presses a member added would make those key presses count as the owner's own on every device. The review of the first design showed that the last point goes further than a label change on an up-to-date device (a device that is a moment behind pushes the member's older content, which differs from the row; a copy is a new row), and that the folder a person shares lies in that person's own profile, where a member's snippet with an early creation time could take over an abbreviation of the owner's private snippets.

**Decision.**
1. **The server enforces no uniqueness on content.** It never reads abbreviations, labels, bodies or names except to store them and compare them for equality. The store keeps refusing a duplicate abbreviation in a local edit; rows that arrive by sync are applied as they are, and the unique index on the abbreviation becomes an ordinary one. Which snippet holds an abbreviation is decided on every device by one order: in the user's personal profile first the snippets whose content the user wrote, then those whose content someone else wrote; then the other folders by the time the server recorded access to them, then by the id of the shared folder; inside one of these by the revision at which the server first accepted the row, then id. No creation time and no device clock takes part. The others are listed in library health.
2. **A share's id is derived** from its folder and its group (SHA-256 of a fixed prefix and the two ids, as a UUID of version 8), so a pair has one row everywhere. A change to a share that was made without seeing the row's latest revision is not applied; a delete of a share always is. A share gives its members what is in the folder and never the folder itself: the shared folder is renamed, moved and deleted by its owner only, also when it is a sub-folder of the owner's tree, and a folder above the root of another share is deleted only by who may end that share. In a family every member may share a folder with the group, in a team its owner and admins (open question 7).
3. **Profiles, memberships and invitations are written by the server only**, through account calls that need a connection. Devices receive them through the feed and never queue them. The ownership of a group changes when the member it is offered to accepts (open question 11). An invitation is matched to an account by the address the authentication service holds as confirmed, never by a claim of the token.
4. **Access entries.** The server keeps one row per user and readable folder, with the permission and the time access began, in step with shares and memberships inside the same transactions and under the profile locks of ADR-0027. The read policies look it up, the visibility entries of the feed are its additions and removals, and each device receives its own entries instead of computing permissions. A shared folder its owner deletes ends, for the people it was shared with, as any share ends.
5. **Authorship of content.** The server sets `updated_by` from the caller, and for a snippet also `content_by` and `content_at`: who last changed its abbreviation, kind, body, trigger, case mode or word-start flag. The writer is named only when those fields, as sent, differ both from the row and from the version the write was based on; when they equal the base version, the base's author stays; when the server cannot tell, the author is nobody, which every device treats as someone else. A device holds a snippet for review when `content_by` is not its user and the content needs review under ADR-0022, and it stores what it approved as those six fields, not as a revision number; a revision whose six fields equal the approved ones does not ask again, and an approval names the content the dialog showed. A snippet that is held cannot be copied, duplicated or moved to another profile until it is reviewed, because a copy is a new row whose author is its creator. A `{snippet}` reference written by someone else is held like a key press, because it types the reader's own snippets; this adds a fifth item to ADR-0022's list and is the owner's to confirm (open question 10).
6. **A row never changes its profile.** Moving content between profiles is a copy and a delete made by the device.
7. **Tags, attachments and files of someone else's profile** are readable only through a snippet the reader can read, and for the rows a member wrote there only while that member may still change a folder of the profile. A stored file is never readable because a reader knows its hash, wrote a row that names it, or linked that row from a snippet: an attachment row counts for a file only when it is backed, which the server decides, at the row's creation when its creator can read the file, or when its creator commits an upload of those bytes. A device removes such rows and files when the last link it holds to them goes.

**Consequences.** No edit is refused for a reason the user cannot see at the time they make it; duplicates are visible and each device resolves them the same way. A snippet whose content someone else wrote can never take over an abbreviation of a snippet whose content the user wrote, in shared folders or in the folder owner's own profile, whatever a device's clock says. "Stop sharing" cannot be undone by a device that was offline. Groups and memberships cannot be changed offline, and nobody owns a group without having agreed. The interface and the server cannot disagree about a permission. The review of ADR-0022 cannot be bypassed by the reader's own edit, stale write or copy, and a move or a new label by someone else does not ask the user again. The store gains device-local tables (access, origin of content, approved content, kept changes, skipped rows) and loses a unique index; the model's entities are unchanged, and each row gains one server-set number, the revision of its first acceptance. Because the server does not interpret content, the content columns could hold ciphertext later (ADR-0029).

**Rejected.** A unique index on the server per profile (cannot cover a user's view across profiles, and turns a duplicate into an edit that never syncs). Renaming a duplicate automatically (changes what the user types without asking). Ordering duplicates by the creation time a device sends (a member's device, or a wrong clock, could date a snippet before the owner's and take its abbreviation). Random ids for shares with a uniqueness check (a re-share after "stop sharing" cannot be told from a stale share). Memberships queued on the device (access granted by a row the server has not checked against the plan and the invitation). Binding an approval to a revision number (asks again after every label change and can be bypassed through the row's last writer). Naming the writer as author whenever the pushed content differs from the current row (a reader's device that is a moment behind would turn a member's unreviewed content into the reader's own). Letting the author of a tag or attachment row read it for good (a removed member kept reading, and a known hash gave a file). Counting every link from a readable snippet for a file (a member could write a row with a known hash, link it, and read a file they never had). Computing permissions on the device from shares and memberships (two implementations of one rule).
