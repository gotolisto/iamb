# ADR-0030: Installers: a universal disk image, a per-user NSIS installer, signing only when the owner's secrets exist

Status: proposed (task 5.1)

**Context.** Task 5.1 ships Iamb as installers: "notarized macOS disk image, signed Windows installer; install on clean machines; 0 security warnings on either OS". ADR-0021 already fixes that the macOS service is a signed helper app with the bundle identifier `org.iamb.Iamb.Service` inside `Iamb.app`, registered as a login item by the main app, that the Windows supervisor is started from the per-user Run key, and that installing needs no administrator rights on either system. The UI host finds the service next to its own executable on Windows (`iamb-platform-windows`, `login_item.rs`) and by bundle identifier under `Iamb.app/Contents/Library/LoginItems/` on macOS (`iamb-platform-macos`, `login_item.rs`). The repository is public and the owner holds the certificates; the pipeline has to work, and say plainly that it is unsigned, before they are added.

**Decision.**

1. *macOS:* one universal `Iamb.app` (Apple silicon and Intel in each binary) in a `.dmg`, minimum macOS 13 (the login-item API). The service ships as `Iamb.app/Contents/Library/LoginItems/Iamb Service.app` (identifier `org.iamb.Iamb.Service`, `LSUIElement`), built by `apps/desktop/release/macos/build-helper.sh` and copied in through the bundler's `macOS.files`. The helper is signed before the bundler signs the outer app (the bundler does not sign custom files, and the outer seal needs nested code signed first). Both use the hardened runtime with empty entitlements: Accessibility and Input Monitoring are user grants, not entitlements, for an app outside the sandbox. The system starts a login item without arguments, so `iamb-service` run from that layout defaults to `--supervise`. When signed, the bundler notarizes and staples the app, and the pipeline notarizes and staples the disk image too.
2. *Windows:* the bundler's NSIS installer with `installMode: currentUser`, into `%LOCALAPPDATA%\Iamb`, with `iamb-service.exe` beside `iamb-desktop.exe` (the bundler's `externalBin`). Installer hooks stop this user's running service before files are replaced or removed, start it again after an install if "start at login" is on, and take the Run value away on uninstall (moved aside so that an upgrade that uninstalls first puts it back).
3. *Linux:* a `.deb`, unsigned, as a by-product (Linux is a development platform, architecture §3.3).
4. *Signing is on only when the secrets exist.* macOS: the six variables the bundler reads (`APPLE_CERTIFICATE`, `APPLE_CERTIFICATE_PASSWORD`, `APPLE_SIGNING_IDENTITY`, `APPLE_ID`, `APPLE_PASSWORD`, `APPLE_TEAM_ID`); all or none, a partial set fails the build. Windows: either a code-signing certificate as a `.pfx` (`WINDOWS_CERTIFICATE`, `WINDOWS_CERTIFICATE_PASSWORD`, used by thumbprint through `signtool`) or a sign command (`WINDOWS_SIGN_COMMAND`, the bundler's `signCommand`, for a cloud signing service or hardware token). Without them the builds are unsigned (ad hoc on macOS, so the bundle is still sealed) and the job summary says so.
5. *One version:* `[workspace.package] version` in `Cargo.toml`. `tauri.conf.json` has no `version` (the bundler then takes the crate's), and `cargo xtask release-version --tag` fails a tag that is not `v` + that version.
6. *Install smoke test* on fresh hosted runners that did not build the installer: install silently, check files, identifiers and versions, start the installed UI host once (`--measure-open 1`), verify signatures when signed, uninstall, check it is gone. It runs in every release and on demand from CI, not on pull requests.

**Consequences.** No administrator rights to install, update or uninstall on either OS; nothing machine-wide. One macOS download fits every Mac; builds take longer (two architectures). Releases can be cut before the certificates exist, and every artifact says whether it is signed. Unsigned builds raise the system's warnings (docs/release.md), and in a release build the service's installed-binary check (architecture §8, open finding 11) refuses the UI host until signing and the peer check of task 5.2 land, so unsigned release installers are for testing the installer, not for users. On Windows a signature alone does not silence SmartScreen until the publisher has reputation.

**Rejected.** MSI (the bundler's WiX installer installs per machine and needs administrator rights, against ADR-0021). The service as a bare executable in `Contents/MacOS` on macOS (ADR-0021: grants attach unreliably; the login-item API needs a helper app). Two macOS disk images, one per architecture (users must pick; the universal build costs CI time only). Failing the release when secrets are missing (the pipeline could not be tested before the owner buys certificates). Signing in the smoke test or from pull requests (secrets would reach code that has not been reviewed).
