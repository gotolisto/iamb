# ADR-0027: Sync rules: the server's order, writes through functions, deletes as writes, nothing unsent is overwritten

Status: proposed (task 4.1; awaiting the owner's approval). Adds to ADR-0016, whose frame it keeps.

**Context.** ADR-0016 fixed the frame of sync (a change feed per user, last write wins per row with history, an outbox with base revisions, soft deletes purged after 30 days) and left the rules to task 4.1. The rules must give every conflict a defined outcome, lose no edit in a simulation of 1,000 runs with offline periods and clock skew, keep two online devices in step within 5 seconds, and survive lost answers, repeated requests, a restored server and devices that return after months. `docs/sync-design.md` holds the full design and `spec/sync/scenarios.toml` the scenarios.

**Decision.**
1. **Order.** The last write is the one the server accepts last. The server gives each accepted write a revision from one growing counter and its own time. Device clocks decide nothing; a device's creation time for a row is kept but never later than the server's clock.
2. **Writes go through functions.** Tables have row-level security with read rules only. A device sends up to 200 changed rows to one database function, each with the revision it was based on and an id; the function checks permissions against the current state, writes the row, the history, the conflict, the feed entries and the access entries in one transaction, answers each row by itself, and keeps each answer for 30 days so that a repeated change writes nothing.
3. **Rows, not fields.** A write replaces the whole row. A write based on an older revision still wins, and a conflict is recorded when another device had changed a recorded field or the row's liveness since; both authors see it and either can restore the other version, which the server writes as a new revision. A folder's position is replaced without a record.
4. **Deletes are writes.** Of an edit and a delete, whichever arrives last wins and the other is offered back. A folder's delete takes its whole subtree and its shares as the server has them, with a conflict for each row the deleting device had not seen. A live row written into a deleted folder restores the folders above it, if the writer may, without what was deleted in them and without their shares.
5. **Structure is put right.** A move that would close a cycle or make a fifth level keeps the folder's place (a new folder goes one level up) and the device is told. A row never changes its profile.
6. **The device never overwrites an unsent change with a pulled row.** Its own push follows and wins, and the server keeps the version it skipped, with the conflict. Outbox entries are sent as one change per row (the row as it is now, the base of its oldest entry).
7. **Refused and blocked changes are not dropped.** A change the server refuses for good (no permission, the row or its folder purged) is kept on the device in a list for the user, and the server's state replaces the local row. A change the server cannot store yet (too large, over a plan's limit) stays on the device with its row, marked.
8. **Pull.** A device reads its feed in pages from one position, stored in the same transaction as the page's effects. The live channel carries only the feed's head; without it the device polls every 2 seconds while active. A position older than the 30 days of the feed, or from before a restore of the server, makes the device fetch everything and reconcile, leaving unsent changes alone.
9. **Restore.** A restored server starts a new epoch, and devices send back the rows they hold in revisions newer than the backup.

**Consequences.** Every scenario of `spec/sync/scenarios.toml` has one outcome that follows from numbered rules. A wrong clock cannot make devices disagree. Retries are safe by construction. Nothing a user made disappears without being on the server, in a conflict, or in a list on the device that made it. The server's functions carry the logic that policies alone could not (history, feed and access in one transaction), which is more to review in task 4.3 and is testable there call by call. Conflicts are per row: two people who change different fields of one snippet get a conflict and one of the changes must be redone or restored by hand. An edit to a row deleted more than 30 days ago does not bring the row back.

**Rejected.** Merging fields (ADR-0016 already declines it: a merged snippet is a revision nobody wrote or approved, and the fields of a snippet are one behaviour); it could be added on the server later without changing the protocol. Edits always beating deletes (a second rule to remember, and a deleted folder would come back whole from one late edit). Direct table writes under write policies (the previous version, the history and the feed cannot be kept consistent from policies and triggers that a client's statement shapes). Refusing a write whose base is stale and making the device merge (an edit would exist on one device only until its user acted, so online devices would not agree). Applying a pulled row over an unsent change and re-basing the change (the device does not keep the base content). Content in the live channel (a second path for applying changes, and content on a channel that is harder to authorise).
