# ADR-0027: Sync rules: the server's order, writes through functions, deletes as writes, nothing unsent is overwritten

Status: proposed (task 4.1; awaiting the owner's approval; revised after the independent review of the design, `docs/reviews/4.1-sync-design-review.md`). Adds to ADR-0016, whose frame it keeps.

**Context.** ADR-0016 fixed the frame of sync (a change feed per user, last write wins per row with history, an outbox with base revisions, soft deletes purged after 30 days) and left the rules to task 4.1. The rules must give every conflict a defined outcome, lose no edit in a simulation of 1,000 runs with offline periods and clock skew, keep two online devices in step within 5 seconds, and survive lost answers, repeated requests, requests that arrive together, a restored server, copied data directories and devices that return after months. `docs/sync-design.md` holds the full design and `spec/sync/scenarios.toml` the scenarios. The review of the first design found sequences in which a device moved past a row it had not applied and never heard of it again, and a decision the design had left out: what two requests at the same moment may assume about each other. Points 2, 4, 6, 8 and 9 below carry the answers.

**Decision.**
1. **Order.** The last write is the one the server accepts last. The server gives each accepted write a revision from one growing counter and its own time. Device clocks decide nothing; a device's creation time for a row is kept for display and never later than the server's clock.
2. **Writes go through functions, one profile at a time.** Tables have row-level security with read rules only. A device sends up to 200 changed rows to one database function, each with the revision it was based on and an id; the function checks permissions against the current state, writes the row, the history, the conflict, the feed entries and the access entries in one transaction, answers each row by itself, and keeps each answer for 30 days so that a repeated change writes nothing. Every writing transaction first takes its locks in one fixed order, before it reads anything it decides on: the calling device's row, the profile rows of the groups it touches by id, the profile rows of the personal profiles it touches by id, and at the end the feed heads by user id. Writes to one profile are therefore serial and each sees what the one before committed, so two requests that arrive together can never commit a folder cycle, a live row under a deleted folder, or access for a share that has just ended. The work of one request is bounded (a folder's delete takes at most 2,000 rows with it per request and is finished in parts), and every function carries its own time-out.
3. **Rows, not fields.** A write replaces the whole row. A write based on an older revision still wins, and a conflict is recorded when someone else had changed a recorded field or the row's liveness since: another device, or the same device id under a change the write does not name as its own earlier one. All authors see it and any of them can restore a replaced version, which the server writes as a new revision. A row has one open conflict; a new one takes over the versions the old one offered, so the first loser of three writers stays within reach. A folder's position is replaced without a record.
4. **Deletes are writes.** Of an edit and a delete, whichever arrives last wins and the other is offered back. A folder's delete takes its whole subtree and its shares as the server has them, with a conflict for each row the deleting device had not seen; the answer carries the server's row for every row the device had deleted with the folder, so a row that had left the folder, or a delete that was refused, never leaves a device with rows deleted that the server has live. A live row written into a deleted folder restores the folders above it, if the writer may, without what was deleted in them and without their shares.
5. **Structure is put right.** A move that would close a cycle or make a fifth level keeps the folder's place (a new folder goes one level up) and the device is told. A row never changes its profile.
6. **The device never overwrites an unsent change with a pulled row, and never forgets that it skipped one.** Its own push follows and wins, and the server keeps the version it skipped, with the conflict. The store notes each skipped row and fetches it once the change is settled and the row is still behind. Outbox entries are sent as one change per row (the row as it is now, the base of its oldest entry), and are marked when they are handed to the agent: a row the server may have seen is never dropped unsent, also when the answer was lost and the agent restarted.
7. **Refused and blocked changes are not dropped.** A change the server refuses for good (no permission, the row or its folder purged) is kept on the device in a list for the user, a refused delete included, and the server's state replaces the local row. A change the server cannot store yet (too large, over a plan's limit) stays on the device with its row, marked; so does a change whose request keeps failing, after the agent has narrowed the request down to it, so that it cannot hold up the others for ever.
8. **Pull, positions and devices.** A device reads its feed in pages from one position, stored in the same transaction as the page's effects; visibility changes are handled in the order of the feed. The live channel carries only the feed's head; without it the device polls every 2 seconds while active. A position is issued by the server and accepted once (the one before it once more, for a lost answer), so a second installation with a copied data directory is noticed at its next call and comes back as a device of its own. A session has one device row; a revoked device is refused at once by every function and policy and cannot register again. A position older than the 30 days of the feed, or from before a restore of the server, makes the device fetch everything and reconcile, leaving unsent changes alone and removing afterwards what the server turned out not to hold.
9. **Restore.** A restored server starts a new epoch, with the interface closed until it has. Devices compare row by row and send back the rows the server holds in an older revision or not at all; such a re-push may create a row when its revision lies in the span the restore lost. Rows only the server writes come back as the backup had them; a device whose user had taken access away since (removed a member, withdrawn an invitation) makes that call again, and never one that gives access.

**Consequences.** Every scenario of `spec/sync/scenarios.toml` has one outcome that follows from numbered rules, and the check of the scenarios refuses an outcome that contradicts its own answers. A wrong clock cannot make devices disagree. Retries are safe by construction. Nothing a user made disappears without being on the server, in a conflict, or in a list on the device that made it. The server's functions carry the logic that policies alone could not (history, feed and access in one transaction), which is more to review in task 4.3 and is testable there call by call, including with two connections at once. Writes to one profile wait for each other for the length of a request. Conflicts are per row: two people who change different fields of one snippet get a conflict and one of the changes must be redone or restored by hand. An edit to a row deleted more than 30 days ago does not bring the row back. A restore of the server gives back, for a time, access that was taken away after the backup.

**Rejected.** Merging fields (ADR-0016 already declines it: a merged snippet is a revision nobody wrote or approved, and the fields of a snippet are one behaviour); it could be added on the server later without changing the protocol. Edits always beating deletes (a second rule to remember, and a deleted folder would come back whole from one late edit). Direct table writes under write policies (the previous version, the history and the feed cannot be kept consistent from policies and triggers that a client's statement shapes). Locking only the rows a request writes (two requests that each pass their checks can together commit what neither may; task 4.2 would have had to choose a rule itself). Refusing a write whose base is stale and making the device merge (an edit would exist on one device only until its user acted, so online devices would not agree). Applying a pulled row over an unsent change and re-basing the change (the device does not keep the base content). One answer per pushed op, with nothing for the rows of a cascade (a device kept rows deleted that the server had live). One threshold revision for what to send again after a restore (a counter's value is not a moment in time, and rows the server alone writes never came back). Content in the live channel (a second path for applying changes, and content on a channel that is harder to authorise).
