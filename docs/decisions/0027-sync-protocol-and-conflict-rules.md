# ADR-0027: Sync rules: the server's order, writes through functions, deletes as writes, nothing unsent is overwritten

Status: proposed (task 4.1; awaiting the owner's approval; revised after the independent review of the design, `docs/reviews/4.1-sync-design-review.md`, again after its follow-up, `docs/reviews/4.1-sync-design-followup.md`, and a third time after the close-out review, `docs/reviews/4.1-sync-design-closeout.md`). Adds to ADR-0016, whose frame it keeps. Amended by ADR-0031 (what a conflict offers and to whom, restores, and locks; after the security review of task 4.3).

**Context.** ADR-0016 fixed the frame of sync (a change feed per user, last write wins per row with history, an outbox with base revisions, soft deletes purged after 30 days) and left the rules to task 4.1. The rules must give every conflict a defined outcome, lose no edit in a simulation of 1,000 runs with offline periods and clock skew, keep two online devices in step within 5 seconds, and survive lost answers, repeated requests, requests that arrive together, a restored server, copied data directories and devices that return after months. `docs/sync-design.md` holds the full design and `spec/sync/scenarios.toml` the scenarios. The review of the first design found sequences in which a device moved past a row it had not applied and never heard of it again, and a decision the design had left out: what two requests at the same moment may assume about each other. Points 2, 4, 6, 8 and 9 below carry the answers. The follow-up review found that after a restore an edit could still be replaced unseen, by a row written after the restore that a device took for newer than the edit the restore had lost; that the line between "lost" and "purged" was read from a revision counter, which is not a moment in time; that any client could make the server begin an epoch; and that two lost answers in a row could sign an honest device out. Points 8 and 9 were rewritten for these. The close-out review found that a restore also puts back the sessions of the backup, so that a device can be signed out before it has given anything back, and that a sign-out removed what only that device held; that nothing made a device, or the operator, take away again what had been taken away before rows were given back, so that a folder shared after a removal could reach the person removed; and that a revoked session is still a session at the authentication service, where its holder can set a password. Points 8 and 9 say more for these, and point 10 is new.

**Decision.**
1. **Order.** The last write is the one the server accepts last. The server gives each accepted write a revision from one growing counter and its own time. Device clocks decide nothing; a device's creation time for a row is kept for display and never later than the server's clock.
2. **Writes go through functions, one profile at a time.** Tables have row-level security with read rules only. A device sends up to 200 changed rows to one database function, each with the revision it was based on and an id; the function checks permissions against the current state, writes the row, the history, the conflict, the feed entries and the access entries in one transaction, answers each row by itself, and keeps each answer for 30 days so that a repeated change writes nothing. Every writing transaction first takes its locks in one fixed order, before it reads anything it decides on: the calling device's row, the profile rows of the groups it touches by id, the profile rows of the personal profiles it touches by id, and at the end the feed heads by user id. Writes to one profile are therefore serial and each sees what the one before committed, so two requests that arrive together can never commit a folder cycle, a live row under a deleted folder, or access for a share that has just ended. The work of one request is bounded (a folder's delete takes at most 2,000 rows with it per request and is finished in parts), and every function carries its own time-out.
3. **Rows, not fields.** A write replaces the whole row. A write based on an older revision still wins, and a conflict is recorded when someone else had changed a recorded field or the row's liveness since: another device, or the same device id under a change the write does not name as its own earlier one. All authors see it and any of them can restore a replaced version, which the server writes as a new revision. A row has one open conflict; a new one takes over the versions the old one offered, so the first loser of three writers stays within reach. A folder's position is replaced without a record.
4. **Deletes are writes.** Of an edit and a delete, whichever arrives last wins and the other is offered back. A folder's delete takes its whole subtree and its shares as the server has them, with a conflict for each row the deleting device had not seen; the answer carries the server's row for every row the device had deleted with the folder, so a row that had left the folder, or a delete that was refused, never leaves a device with rows deleted that the server has live. A live row written into a deleted folder restores the folders above it, if the writer may, without what was deleted in them and without their shares.
5. **Structure is put right.** A move that would close a cycle or make a fifth level keeps the folder's place (a new folder goes one level up) and the device is told. A row never changes its profile.
6. **The device never overwrites an unsent change with a pulled row, and never forgets that it skipped one.** Its own push follows and wins, and the server keeps the version it skipped, with the conflict. The store notes each skipped row and fetches it once the change is settled and the row is still behind. Outbox entries are sent as one change per row (the row as it is now, the base of its oldest entry), and are marked when they are handed to the agent: a row the server may have seen is never dropped unsent, also when the answer was lost and the agent restarted.
7. **Refused and blocked changes are not dropped.** A change the server refuses for good (no permission, the row or its folder purged) is kept on the device in a list for the user, a refused delete included, and the server's state replaces the local row. A change the server cannot store yet (too large, over a plan's limit) stays on the device with its row, marked; so does a change whose request keeps failing, after the agent has narrowed the request down to it, so that it cannot hold up the others for ever.
8. **Pull, positions and devices.** A device reads its feed in pages from one position, stored in the same transaction as the page's effects; visibility changes are handled in the order of the feed. The live channel carries only the feed's head; without it the device polls every 2 seconds while active. A position is issued by the server, which keeps two for each device: the one it issued last and the one that was presented for it. A call is accepted with either, and every answer that issues a position sets the pair again, so the same position can be presented any number of times after answers that did not arrive, while a second installation with a copied data directory, which presents neither, is noticed at its next call and comes back as a device of its own. A session has one device row; a revoked device is refused at once by every function and policy, and its row is kept for as long as its session exists, because the platform cannot end one other session: it cannot register again, a day or a year later. A session is accepted only when its token says that it was opened the way Iamb signs in, by a link or a code sent to the account's address or by an identity provider: a session opened with a password, which the holder of a revoked session can set at the authentication service, is refused by every function and policy. A null row for a folder ends that tree on the device as a purge does, except the parts of it that are shared by themselves, so the rows of a tree that leaves a user's sight and its revocation can arrive in any order and a part that stays readable stays on the device; the daily access check also fetches a readable folder the device lacks. A position older than the 30 days of the feed, or from before a restore of the server, is refused to a pull and to a push alike and makes the device fetch everything and reconcile, leaving unsent changes alone and removing afterwards what the server turned out not to hold.
9. **Restore.** A restored server starts a new epoch, with the interface closed until it has. Only the operator begins an epoch: a device that reports more than the server holds is told to wait and the operator is alerted, and nothing a client sends changes the server's state. What the restore lost is measured per profile: every writing transaction holds its profile's lock and records the last revision it drew on the profile's row, so in the restored database that number is exactly the last revision of the profile the backup holds; the value of the revision counter is not used for this. The new epoch's revisions start at a number taken from a time, the later of the server's clock and a floor the operator passes from the function log, which lies above every revision a device can hold, also after a second restore from an older backup and with a clock that is behind. A device sends again every row it holds in a later revision and may write, or whose version its own user wrote, whatever the server holds by then, and nothing the server sends replaces such a row before it was sent; a version its user may no longer write is kept on the device for the user. On the server such a re-push is applied over a row untouched since the restore, wins as a stale write with a conflict over a row written since, yields to a later lost version of the same row while staying on offer, and may create a row; the row remembers the latest lost version it has taken in, also across later writes, so that an earlier one that arrives late replaces neither. Rows only the server writes come back as the backup had them. What took access away since the backup is taken away again before anything is given back: the operator's restore script makes those calls again from the function log before the server is opened, and each device keeps its own list of the calls by which its user took access away (removed a member, withdrew an invitation, revoked a device), written before each call and completed with a mark the server gave, and makes again those the restore lost before it sends a row, then the deletes of shares and the folders, then the rest. Neither makes a call that gives access. The stored files are not part of the database's backup: the script puts rows and files in step, and devices offer their files again. The history and the conflicts of the lost time do not come back.
10. **Signing out.** The user's own library stays on a device that is signed out. What belongs to other people is removed only on the server's word: when the answer that ends the session, or the round of sync that a sign-out by hand makes first, names the epoch the device is in. Every other sign-out (a session the authentication service refuses, a refusal that names another epoch, a sign-out without a connection) sets those folders aside, unused and unseen, until the same account has signed in again and synced, and for 30 days at most; what the device's own user wrote there in the last 30 days is then kept in the list of changes that were not synced. A restore puts back the sessions of the backup and can end a device's session before the device has learned of it; a device that is signed out this way still gives back what it holds, after its user's next sign-in.

**Consequences.** Every scenario of `spec/sync/scenarios.toml` has one outcome that follows from numbered rules, and the check of the scenarios refuses an outcome that contradicts its own answers. A wrong clock cannot make devices disagree. Retries are safe by construction. Nothing a user made disappears without being on the server, in a conflict, or in a list on the device that made it. The server's functions carry the logic that policies alone could not (history, feed and access in one transaction), which is more to review in task 4.3 and is testable there call by call, including with two connections at once. Writes to one profile wait for each other for the length of a request. Conflicts are per row: two people who change different fields of one snippet get a conflict and one of the changes must be redone or restored by hand. An edit to a row deleted more than 30 days ago does not bring the row back. A restore of the server gives back access that was taken away after the backup only where the function log does not name the call, and then until the device that took it away has synced; after it every user may have to sign in again; it loses the versions that had already been replaced in the lost time, and can show a conflict between two versions of which one was written knowing the other, because the record of that is gone. A profile's row is written by every transaction in the profile. A revoked device's row stays for as long as its session does, which can be for good. A device that is signed out without the server's word holds other people's folders, set aside, for up to 30 days. The restore procedure depends on a function log that outlives the database.

**Rejected.** Merging fields (ADR-0016 already declines it: a merged snippet is a revision nobody wrote or approved, and the fields of a snippet are one behaviour); it could be added on the server later without changing the protocol. Edits always beating deletes (a second rule to remember, and a deleted folder would come back whole from one late edit). Direct table writes under write policies (the previous version, the history and the feed cannot be kept consistent from policies and triggers that a client's statement shapes). Locking only the rows a request writes (two requests that each pass their checks can together commit what neither may; task 4.2 would have had to choose a rule itself). Refusing a write whose base is stale and making the device merge (an edit would exist on one device only until its user acted, so online devices would not agree). Applying a pulled row over an unsent change and re-basing the change (the device does not keep the base content). One answer per pushed op, with nothing for the rows of a cascade (a device kept rows deleted that the server had live). One threshold revision for what to send again after a restore (a counter's value is not a moment in time: Postgres logs a sequence up to 32 values ahead and outside any transaction; and rows the server alone writes never came back). Taking the server's row after a restore whenever its revision is the higher one (a write made after the restore is not newer than an edit the restore lost). An epoch that the server begins by itself when a device reports more than it holds (any signed-in client can send that report). Keeping the last two positions issued (after two lost answers the honest device holds neither). Removing a revoked device's row after a fixed time (the session outlives it, and registers again). Removing other people's folders at every sign-out (a restore ends sessions before the devices have given back what only they hold). Giving rows back after a restore in the order they were queued (a share, or a snippet in a folder whose share had ended, reaches a person who had been removed). Leaving lost removals to the device that made them alone (another device of the same user gives a share back first). Ending a revoked device's session by removing its row at the authentication service (the computer could no longer be told that it was revoked, and whether the functions' owner may do it is not known). Relying on a setting of the authentication service to keep passwords out (none was found; the check is in Iamb's own functions). Content in the live channel (a second path for applying changes, and content on a channel that is harder to authorise).
