# ADR-0029: Synced content is readable by the server in version 1; the server never interprets it

Status: proposed (task 4.1; open question 2 of `docs/sync-design.md` §13 is the owner's).

**Context.** Architecture §8 promises that typed text never leaves the machine and treats other members of shared folders as untrusted. It does not say whether the server may read what is synced. Snippets can hold addresses, bank details and signatures, so the answer has to be stated before anything is stored. End-to-end encryption is possible, but sign-in has no password to derive a key from, sharing needs a key per folder handed to each member by a device that already has it, and a shared folder must appear within 10 seconds.

**Decision.** In version 1 synced rows and attachment files are protected in transit (TLS) and at rest (the hosting provider's volume encryption) and are readable by the server and its operator. The privacy text says so in plain words. Typed text, fill-in values, clipboard content, usage counts, settings, approvals and diagnostics are in no synced row and never reach the server (architecture §8, ADR-0015). The server is built so that it never interprets content: no uniqueness, search or parsing on abbreviations, labels, bodies or names (ADR-0028), only storage and equality. The server is trusted for the integrity of what it delivers, including the author it reports for a snippet's content.

**Consequences.** Sharing, invitations, recovery after losing every device and the 10-second target need no key handling. Whoever operates or breaks into the server can read synced snippets and could alter them; hosting controls and the security review of task 4.3 are the defence. End-to-end encryption can be added later as a mode of a profile without changing the conflict rules: the content columns would hold ciphertext, and the two places where the server compares content would compare a hash the device sends.

**Rejected.** End-to-end encryption in version 1 (a recovery key every user must keep, key hand-over that depends on a member's device being online, re-keying on removal, no server-side check of attachment hashes; about a phase of work across tasks 4.2 to 4.6). Encrypting only the body with a key the server holds (the operator can still read it; it adds nothing to volume encryption). Saying nothing (users would assume more than is true).
